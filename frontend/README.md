# RockCRM — фронтенд, этапы 1–5

**Этап 1** (`docs/contract-v1.md`): расписание филиала на день и панель
отметки посещаемости с предпросмотром последствий.

**Этап 2** (`docs/contract-v2.md`): экран «Ученики» с поиском по родителю,
карточка ученика, продажа и продление абонемента, заморозка. У продажи
и заморозки — предпросмотр итога до подтверждения, тот же принцип,
что и у отметки.

**Этап 3** (`docs/contract-v3.md`): воронка заявок — доска по стадиям
с перетаскиванием и откатом при отказе сервера, карточка заявки,
назначение пробного урока с видимой занятостью и подтверждением
овербукинга, конверсия в ученика с продажей абонемента и отчёт
по воронке.

**Этап 4** (`docs/contract-v4.md`): экран «Деньги и ЗП» — сводка (выручка
со сравнением, загрузка кабинетов, ведомость, «требует внимания»), ведомость
по преподавателям с раскрытием в расшифровку по занятиям, закрытие периода
с подтверждением и предупреждением о необратимости, отчёты по выручке,
загрузке кабинетов и долгам.

**Этап 5** (контракта не было, формы — в `backend/README.md`, пункты 40–44):
настоящий вход. Экран входа в два шага — телефон и одноразовый код, — вкладка
пароля для сотрудников, сессия в куке `HttpOnly`, меню и экраны по роли
из `GET /auth/me`, выход и «выйти на всех устройствах».

**Этап 5, вторая половина** (`docs/contract-v5.md`): кабинет родителя —
отдельный простой макет с ресурсами `/me/*`. Главный экран с ближайшим
занятием крупно и остатком абонемента, расписание на неделю со всеми детьми
сразу, карточка ребёнка с заметками, домашним заданием и репертуаром, заявка
на перенос и заявка на продление. Мобильный вид первичен.

**Это ломающее изменение.** Заголовков `X-Tenant-Id` и `X-User-Id` больше
не существует, переменные `VITE_TENANT_ID` и `VITE_USER_ID` удалены, и любой
запрос без сессии отвечает `401`. Старый `.env.development.local` с этими
ключами работать не мешает, но и ни на что не влияет.

Визуальный ориентир — `prototype/index.html`.

> В репозитории может лежать `.env.development.local` с `VITE_USE_MOCKS=false`
> — переключение на живой бэкенд. Эндпоинтов свежего этапа там может ещё
> не быть: чтобы посмотреть новые экраны, поставьте в этом файле `true`
> или удалите его.

## Как запустить

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

По умолчанию dev-сервер стартует **на моках**: значения лежат
в `.env.development`, бэкенд не нужен.

Другие команды:

```bash
npm run build        # проверка типов + продакшен-сборка
npx tsc --noEmit     # только проверка типов
```

## Мок-режим

Включается переменной окружения `VITE_USE_MOCKS`.

| Переменная | Смысл |
|---|---|
| `VITE_USE_MOCKS` | `true` — данные из мок-сервера, `false` — запросы к бэкенду |
| `VITE_API_BASE_URL` | базовый путь API, по умолчанию `/api/v1` |
| `VITE_PROXY_TARGET` | куда dev-сервер проксирует `/api`, по умолчанию `http://127.0.0.1:8000` |
| `VITE_TENANT_SLUG` | слаг школы для формы входа, если его негде взять из поддомена |
| `VITE_MOCK_ROLE` | роль мок-сессии: `owner`, `admin`, `teacher`, `guardian`, `student` |
| `VITE_MOCK_SIGNED_OUT` | `true` — моки стартуют без сессии и показывают экран входа |
| `VITE_MOCK_LATENCY_MS` | задержка мок-ответов, чтобы состояние загрузки было видно |
| `VITE_SCHOOL_PHONE`, `VITE_SCHOOL_WHATSAPP` | запасные контакты школы для кабинета родителя, пока их нет в `GET /auth/me` (пробел 36) |

`VITE_TENANT_ID` и `VITE_USER_ID` **удалены**: заголовков-заглушек больше нет,
школу определяет сессия.

Работа против настоящего бэкенда:

```bash
# .env.development.local — именно так, не .env.local
VITE_USE_MOCKS=false
VITE_PROXY_TARGET=http://127.0.0.1:8000
```

Файл обязан быть `.env.development.local`. В Vite режимный файл
`.env.development` перебивает `.env.local`, поэтому переключение через
`.env.local` молча не сработает: интерфейс останется на моках,
и это выглядит как «всё работает», пока не заметишь, что данные
не меняются после пересева базы.

Школа выбирается не переменной, а тем, кто вошёл: тенант определяет сессия.
Чтобы посмотреть экран денег на тенанте симуляции (155 учеников и полгода
истории), войдите его владельцем — слаг школы поставьте в `VITE_TENANT_SLUG`
(`SELECT slug FROM tenant` покажет доступные). Демо-школа `rockschool-demo`
тоже отвечает, но в ней три преподавателя и шесть занятий за месяц.

Обращаться к API нужно по `127.0.0.1`, не по `localhost`: на Windows
«localhost» сначала пробуется по IPv6, и это добавляет к каждому запросу
секунды. И то, и другое уже прописано — в `vite.config.ts` и в `CORS_ORIGINS`
бэкенда.

Демо-данные бэкенда лежат на **12 августа 2026**, а интерфейс открывается
на сегодняшней дате и берёт первый филиал по алфавиту. На живом API
переключите дату и выберите «Аль-Фараби 53В», иначе увидите пустой день —
это не ошибка, там действительно нет занятий.

### Что в моках

`src/api/mocks/data.ts` повторяет день из прототипа: **12 августа 2026**,
филиал «Аль-Фараби 53В», те же преподаватели (Шарапов, Федько, Мадратов,
Меренков, Исенова) и ученики (Амина Сагындык, Даниал Ким, Марк Ли и др.).
12 занятий, 1 пробный, 1 конфликт кабинета — «Барабанная A» занята
Ержаном Оспановым 12:30–13:25 и пробным Алисы Ким 13:00–13:45.

Дни для проверки состояний:

- **12 августа** — рабочий день: планируемые, проведённое, прогул, пробный, группа;
- **11 августа** — день уже отмечен целиком (панель показывает применённые последствия);
- **13 августа и далее** — пустой день;
- **филиал «Абая 124»** — свой набор занятий.

Особые случаи в данных:

- **Дмитрий Со, 20:00** — на абонементе 0 занятий: предпросмотр предупреждает,
  `POST` возвращает `422` с текстом сервера;
- **Ансамбль «Пятый лад», 17:30** — групповое занятие, четыре участника,
  у каждого свои эффекты и своя отметка;
- **Алиса Ким (пробный)** и **Дамир Ералы** — без абонемента, занятие идёт
  разовой оплатой;
- **Мадина Абишева (2 занятия), Амир Жанат (2), Ержан Оспанов (1)** —
  после списания остаток ≤ 2 и приходит `alerts` о продлении.

Мок-сервер держит состояние в памяти вкладки: отметка меняет остаток
абонемента и статус занятия, повторная отметка того же ученика даёт `409`.
Перезагрузка страницы возвращает исходный день.

**Отмена отметки** (`DELETE /attendance/{id}`) возвращает занятие на абонемент,
снимает начисление преподавателю и снимает саму отметку — после неё ученик
снова доступен для отметки, и мок это разрешает (см. «Отмена отметки» ниже).
Отметки из фикстур — день **11 августа** — тоже получают `attendance_id`,
поэтому кнопка отмены есть и там. Повторная отмена той же отметки даёт `409`.

### Данные этапа 2

Ученики из расписания дополнены профилем (возраст, направление, филиал,
семья), к ним добавлены семьи, тарифы, журнал абонемента, заметки
и отработки. Продажа и заморозка меняют состояние: новый абонемент виден
и в карточке, и в расписании — остаток берётся из одного объекта.

Сценарии для проверки:

- **Амина Сагындык** — карточка из прототипа: семья Сагындык, плательщик
  Гульнара `+77015550003`, скидка 10%, второй ребёнок Тимур (гитара),
  абонемент «Барабаны, 2 раза в неделю, 55 мин» 5 из 8, отработка до
  1 сентября, журнал из пяти движений, три заметки, риск оттока «Средний».
- **Поиск по родителю** — «Гульнара» и `5550003` находят обоих детей.
  Телефон ищется по цифрам, поэтому `+7 701 555 00 03`, `87015550003`
  и `5550003` дают один результат.
- **Продажа**: дата начала подставляется как следующий день после конца
  текущего абонемента — это единственный вариант без `422`. Дата внутри
  действующего периода блокируется ещё в предпросмотре.
- **Промокод**: `RS25` даёт дополнительные 5% (итог 45 900 ₸ при скидке
  семьи 10%), любой другой код — `422` с текстом сервера.
- **Оплата**: снятая галочка «деньги приняты» оформляет абонемент в долг,
  долг попадает в блок семьи.
- **Заморозка**: 14–25 августа — ровно пример контракта: 11 дней,
  срок сдвигается на 11 дней, отменяется ≈3 занятия, лимита остаётся 3.
  Повтор с пересекающимся интервалом даёт `409`, интервал длиннее остатка
  лимита и дата в прошлом блокируются до отправки.
- **Алиса Ким** — ученик без абонемента, семьи, заметок и журнала: все
  пустые состояния карточки видны на одном экране.
- **Семья Абишевых** — долг 27 000 ₸ в блоке семьи.

### Данные этапа 4

Начисления, платежи и закрытые периоды сгенерированы за три месяца
(июнь — 12 августа 2026) детерминированным генератором с зерном: набор
одинаков при каждой перезагрузке, иначе «проверил вчера» ничего не значит.
Июнь и июль закрыты, август идёт.

Сценарии для проверки:

- **`carried_over`** — три отметки за 28–30 июля, поставленные после закрытия
  июля: они приезжают в августовскую ведомость на **+13 200 ₸ / 3 строки**,
  видны отдельной колонкой «Из прошлых», в расшифровке помечены плашкой
  «прошлый месяц» и подсвечены латунным.
- **Закрытие периода**: на августе кнопка гаснет — период не закончился
  (`422 period_not_over` проверяется до отправки). Поставьте «по» **10 августа**
  — диалог покажет, что закрывается (155 начислений, 652 450 ₸), потребует
  галочку «понимаю, что отменить нельзя», и после закрытия ведомость
  переключится на «Период закрыт». Повторное закрытие пересекающегося
  интервала даёт `409 period_overlap`, июль и июнь закрыты в фикстурах.
- **После закрытия** ведомость за весь август показывает только оставшиеся
  строки (11–12 августа), а прошлые правки уходят в закрытый период —
  ровно так же ведёт себя живой бэкенд.
- **Отметка сразу попадает в ведомость**: отметьте кого-нибудь в расписании
  и вернитесь на экран денег — начислений станет на одно больше.
  Отмена отметки добавляет строку-корректировку с минусом, а не правит
  прошлую запись.
- **Ставки различаются** (55 и 85 минут), поэтому у всех преподавателей
  стоит флажок `±` рядом со ставкой.
- **Выручка**: два платежа не привязаны к абонементу и попадают
  в «Не распределено»; строка «Сумма разрезов» сходится с итогом.
- **Долги**: три семьи — Абишевы (27 000 ₸, не платили), Оспановы
  (14 000 ₸ из 28 000) и Жанат (13 500 ₸ из 54 000). Те же суммы видны
  в блоке семьи в карточках их детей.

### Вход в моках

Мок-режим переживает появление входа: он и заведён для разработки без бэкенда.
`VITE_MOCK_ROLE` задаёт роль фиксированной сессии — это способ посмотреть все
пять меню, не заводя пять учётных записей и не пересевая базу между проверками.
Код в моках — `123456`, пароль — `rockschool`; лимиты те же, что у сервера
(три запроса кода, пять неверных попыток), поэтому ветка `429` проверяется
и без бэкенда. По умолчанию сессия уже есть — набирать код на каждой
перезагрузке разработчику незачем; `VITE_MOCK_SIGNED_OUT=true` открывает форму
входа.

Мок-сервер повторяет и два правила видимости, иначе кабинет родителя на моках
показывал бы всю школу и выглядел рабочим: поиск и карточка ученика урезаны
до `student_ids` роли (чужой ребёнок — `404`, а не `403`), а ставка
преподавателя приходит `null` всем, кроме владельца и самого преподавателя.

### Данные кабинета родителя

Фикстуры расписания покрывают два дня (11 и 12 августа), а кабинету нужна
неделя вперёд и назад — иначе ни «ближайшее занятие», ни заявку на перенос
проверить нечем. Поэтому `/me/schedule` отдаёт фикстурные занятия там, где они
есть, и достраивает остальные дни недельным рисунком: Амина — среда и пятница
11:00, Тимур — вторник и четверг 17:00, Дмитрий Со — среда 20:00. Занятие
Тимура **13 августа отменено** — родитель обязан увидеть в расписании
«Отменено», а не пустоту.

Сценарии для проверки (`VITE_MOCK_ROLE=guardian`, вход — Гульнара Сагындык):

- **Двое детей на главном экране.** Амина — 5 из 8, ближайшее занятие
  в пятницу 14 августа 11:00; Тимур — **2 из 8**, предупреждение «абонемент
  заканчивается» и кнопка продления. Остаток Тимура специально приведён
  к порогу: без него половину этапа нечем показать.
- **Заявка на перенос** пятничного занятия Амины проходит; повторная кнопка
  не рисуется, вместо неё «заявка отправлена».
- **Сегодняшнее занятие 12 августа 11:00** — `can_request_reschedule: false`:
  карточка объясняет, почему перенести нельзя, и даёт телефон и WhatsApp.
- **Отменённое занятие 13 августа** — зачёркнуто, с плашкой «Отменено»,
  кнопки переноса нет.
- **Внутренняя заметка Амины за 5 августа** («мама давит на результат»)
  видна в карточке администратора и **не приходит в кабинет**: в истории
  этот день стоит с отметкой «Не пришёл» и без заметки.
- **Репертуар** Амины — семь тегов из трёх видимых заметок, Тимура — четыре.
- `VITE_MOCK_ROLE=student` — Дмитрий Со: один ученик (третья вкладка названа
  его именем), остаток **0**, занятие сегодня в 20:00, и заявка на перенос
  возвращает `422` с текстом сервера прямо в форме.

## Вход и роли (этап 5)

Заголовков-заглушек больше нет. Все запросы идут с `credentials: "include"`,
токен лежит в куке `HttpOnly` — прочитать его из JavaScript нельзя, и это
не неудобство, а смысл: `localStorage` вычитывается первым же XSS вместе
с месячной сессией. Поле `token` в ответе входа фронтенд игнорирует; оно
существует для curl и мобильного клиента.

- **Экран входа — два шага, потому что их два.** Сначала школа высылает код,
  потом человек его вводит: одна форма с двумя полями означала бы пустое поле,
  которое непонятно чем заполнять. Замаскированный номер и обратный отсчёт
  берутся из ответа (`to`, `expires_in`), а не считаются на клиенте.
- **Пароль — отдельной вкладкой и для сотрудников.** Администратор ресепшена
  входит по двадцать раз в день, и SMS на каждый вход — это счёт от оператора,
  а не безопасность. Вкладки разведены состоянием: прислать код и пароль
  вместе — `400`, и такой формы у интерфейса просто нет.
- **`429` — это не `401`, и путать их нельзя.** После `401` человек набирает
  следующий код, после `429` любой набор бесполезен ещё четверть часа. Поэтому
  `429` гасит и отправку, и «выслать заново», и показывает, сколько ждать.
  Окно (15 минут) зашито константой: `Retry-After` сервер не присылает —
  см. пробел 32.
- **Слаг школы берётся из поддомена**, а не спрашивается у человека: родитель
  знает адрес, по которому ему дали ссылку, а не внутренний слаг школы.
  На машине разработчика поддомена нет, поэтому есть `VITE_TENANT_SLUG`
  запасным вариантом — но поддомен главнее: один бандл обслуживает все школы.
- **`GET /auth/me` — первый запрос приложения.** Рабочее пространство
  монтируется только после ответа: иначе первый же экран ушёл бы в API без
  сессии и показал ошибку загрузки вместо формы входа. Роль на клиенте
  не вычисляется нигде — роль, вычисленная клиентом, это роль, которую клиент
  себе назначил.
- **`401` из любого запроса возвращает на вход.** Обработчик один и живёт
  в `api/http.ts`: учить каждый новый запрос тому, что делать с `401`, значит
  однажды забыть. Вход из этого правила исключён — там `401` означает
  «код не подошёл», и сбрасывать форму на каждой опечатке нельзя.
- **Пункт меню, который вернёт `403`, не рисуется.** Он выглядит поломкой
  продукта, а не границей прав. Карта меню лежит в `lib/access.ts` — по флагу
  на каждую проверку бэкенда, с указанием, какую именно:

| | Расписание | Ученики | Заявки | Деньги | Ведомость | Своя ЗП | Продажа |
|---|---|---|---|---|---|---|---|
| `owner` | да | все | да | да | да | — | да |
| `admin` | да | все | да | да | **нет** (`403`) | — | да |
| `teacher` | свои дорожки | свои | нет | нет | нет | да | нет |
| `guardian` | нет | свои дети | нет | нет | нет | нет | нет |
| `student` | нет | себя | нет | нет | нет | нет | нет |

- **У преподавателя «Моя зарплата», а не ведомость.** `GET /payroll` требует
  владельца, но §2 прямо разрешает преподавателю видеть свою ЗП, и
  `GET /payroll/teachers/{staff_id}` со своим `staff_id` ему отвечает.
  Таблица — та же самая, что раскрывается в ведомости владельца: спор о сумме
  разрешается сверкой двух экранов, и они обязаны показывать одно поле одного
  ответа. Вторая «почти такая же» таблица разошлась бы при первой правке.
- **У администратора вкладки «Ведомость» нет, а карточка фонда осталась.**
  `reports/summary` отдаёт ему `payroll.total: null` — на экране прочерк
  и объяснение. Ноль на месте скрытой суммы читался бы как «людям не платят».
- **Родителю поиск не нужен.** Выдачу урезает сервер, поэтому пустой запрос
  для него осмыслен: вернутся его дети. Требовать «введите две буквы»
  от родителя двоих детей значило бы прятать за поиском список из двух строк.
- **Пустой `branch_ids` — это «все филиалы».** Школа из одного филиала связь
  `staff_branch` не заполняет вовсе, и прочтение пустоты как запрета оставило
  бы владельца без единого филиала и без единого экрана. Так же это читает
  и бэкенд.
- **`teacher.rate` стал `int | null`.** `null` — «вам не видно», а не «ставка
  ноль»: прочерк, а не «0 ₸». Ноль однажды попал бы в разговор
  с преподавателем.
- **«Выйти на всех устройствах» стоит рядом с обычным выходом.** Повод у него
  бытовой и срочный — потерянный телефон, уволенный администратор, — и искать
  эту кнопку в настройках человек не станет. Текст подтверждения берётся
  от сервера: «Вы вышли» и «Вы вышли из всех сеансов» — разные действия.
- **Экран входа собран из тех же токенов, что и продукт.** Это первое, что
  видит клиент школы, и другой шрифт с другим акцентом читались бы как чужая
  страница, на которой свой номер вводить не стоит. Новых цветов нет: обе
  темы сверены по вычисленным стилям.

## Кабинет родителя (этап 5)

**Кабинет — отдельный макет, а не урезанный административный.** Права под него
были готовы раньше, но роль `guardian` попадала на экран «Мои ученики», то есть
в тот же интерфейс, только с двумя пунктами меню. Ритм у этого интерфейса чужой:
он собран вокруг смены администратора — плотные таблицы, фильтры, множественные
действия. У родителя один вопрос за раз: когда вести, сколько осталось, что
задали. Поэтому `App` разводит роли до монтирования рабочего пространства:
`guardian` и `student` получают `features/family`, где три экрана, крупный кегль
и ни одной таблицы. Флаг — `access.familyCabinet`, рядом с остальной картой прав.

- **Мобильный вид первичен, а не «тоже поддерживается».** Кабинет открывают
  с телефона в дверях, одной рукой. Правила в CSS написаны для узкого экрана,
  а медиазапрос правит их для широкого, а не наоборот. Навигация внизу — под
  большой палец; на широком экране она уезжает под шапку, потому что там низ
  окна к рукам не ближе. Кнопки высотой 48 пикселей и поля 44 вместо
  административных 34: промах по кнопке на ходу стоит дороже, чем лишние
  двадцать пикселей высоты.
- **Ближайшее занятие — самый крупный кегль на экране** (46 px), и дата рядом
  словами: «Завтра, 14 августа». Одного «Завтра» мало — родитель сверяется
  с календарём, — а одной даты мало для беглого взгляда.
- **Отменённое занятие остаётся в расписании зачёркнутым.** Убрать его значило
  бы оставить родителя гадать, почему в четверг пусто: пустота читается
  как «я что-то перепутал» и заканчивается поездкой к закрытой двери.
- **Расписание — все дети сразу, каждая строка с именем.** Листать детей
  по одному значит собирать неделю в голове, а собирают её ровно тогда,
  когда времени на это нет.
- **Порог «мало осталось» и порог отмены считает сервер.** `ends_soon`
  и `can_request_reschedule` приходят готовыми и на клиенте не пересчитываются:
  это правила школы, а зашитая в интерфейс двойка разъедется с сервером при
  первой правке настроек.
- **Подписи отметок в кабинете свои.** «Прогул без предупреждения» —
  формулировка правила списания, и в истории собственного ребёнка она звучит
  как обвинение; родителю показывается «Не пришёл». Это не смягчение: факт тот
  же, а название пункта регламента родителю ни о чём не говорит.
- **Заявка, а не перенос.** Родитель не двигает расписание сам — слот может
  быть занят, преподаватель может быть занят. Причина обязательна: заявка без
  неё превращается в «перезвоните мне», администратор всё равно звонит
  выяснять, и кабинет не экономит ни одного звонка — то есть не делает того,
  ради чего сделан. Удобное время необязательно: пустое обязательное поле
  выгнало бы звонить ровно туда, откуда кабинет должен уводить.
- **Смещение пояса берётся из строки самого занятия**, а не пишется цифрой, —
  то же правило, что у пробного урока этапа 3.
- **Телефон и WhatsApp стоят в шапке на каждом экране.** Оплаты в кабинете нет
  намеренно, и без этой строки «абонемент заканчивается» упирается в тупик:
  понял, а сделать ничего не может. Контакты повторены и в заявке на продление,
  и в карточке занятия, которое переносить уже поздно, — там, где родитель
  упирается в отказ, выход обязан стоять рядом с отказом.
- **История и репертуар — в карточке ребёнка, а не на главном.** Остаток
  отвечает на вопрос «сколько ещё», репертуар — на вопрос «а есть ли толк»,
  и второй задают реже, но именно он решает, продлевать ли. На главном экране
  он отодвинул бы вниз ответ, ради которого кабинет открыли.
- **Домашнее задание выделено полосой внутри заметки**: за ним заходят вечером,
  и искать его в абзаце преподавательского текста родитель не должен.
- **`ownStudentsOnly` в `access.ts` остался, но больше никем не достигается**:
  роли, у которых он истинен, теперь уходят в кабинет. Флаг описывает реальную
  проверку бэкенда (`GET /students` урезает выдачу по роли), и удалять его
  значило бы удалить документированный факт; если родителю однажды понадобится
  поиск, экран уже готов.

## Решения по стеку

**React 18 + TypeScript + Vite** — задано контрактом.

**Никакой библиотеки состояния.** Состояние приложения — выбранный филиал,
дата, открытое занятие, открытый экран и строка поиска. Кэш между экранами
не нужен: карточка ученика после продажи обязана перечитаться, а не
показать сохранённое. Redux/Zustand добавили бы слой без задачи. Загрузка
данных вынесена в `src/lib/useAsync.ts` (30 строк): состояния
`loading/error/data`, ручной `reload` и отбрасывание ответов на устаревшие
запросы по счётчику поколений — на поиске с задержкой ввода это как раз
и нужно. TanStack Query станет осмысленным, когда появится общий кэш
между экранами денег и учеников.

**Никакого роутера.** Экрана четыре с половиной, ссылками на карточку
пока не делятся, `react-router` добавил бы зависимость ради одного `switch`.
Экран хранится состоянием, «Назад» из карточки возвращает туда, откуда
пришли, — в расписание или в поиск. Как только понадобится «отправь мне
ссылку на карточку», роутер станет оправдан.

**Обычный CSS с переменными, без препроцессоров и UI-китов.** Токены
прототипа (палитра, шрифты, тени) — это уже дизайн-система в CSS-переменных;
tailwind или styled-components заставили бы переписать их в третьей форме.
`src/styles/tokens.css` — токены и обе темы, `src/styles/app.css` — компоненты.
Классы и структура намеренно совпадают с прототипом (`.les`, `.track`,
`.rule`, `.pill`), чтобы правку из прототипа можно было перенести напрямую.

**Ноль рантайм-зависимостей, кроме react и react-dom.** Даты форматируются
вручную (`src/lib/format.ts`): нужны русские месяцы, сдвиг на день
и разбор ISO-строки — date-fns ради этого не нужен.

Зависимости зафиксированы точными версиями: `react`/`react-dom` 18.3.1,
`vite` 5.4.11, `typescript` 5.6.3, `@vitejs/plugin-react` 4.3.4.

Ключевые решения интерфейса:

- **Расписание — многодорожечный секвенсор.** Дорожка = преподаватель,
  ось X = время, ширина блока = длительность. Конфликты и «дыры» в дне
  видно без чтения. Дорожка позиционируется в единицах `--hw` (ширина часа),
  поэтому масштаб меняется одной переменной.
- **Время не проходит через `Date`.** ISO-строка уже несёт смещение филиала;
  `new Date()` пересчитал бы её в пояс браузера, и администратор в Алматы
  увидел бы расписание по времени своего ноутбука. Часы и минуты берутся
  из строки регуляркой (`wallTime`, `wallMinutes`).
- **Фон занятия кодирует отметку, а не статус.** После отметки `status`
  у всех занятий становится `held`, а администратору важно, пришёл ученик
  или прогулял: зелёный — пришёл/опоздал, красный — прогул, серый —
  отменено, латунный — пробный.
- **Последствия не считаются на клиенте.** Панель показывает
  `mark_effects[отметка]` из `GET /lessons/{id}` дословно, включая
  `summary`. Клиентский расчёт разошёлся бы с сервером — это худший
  из возможных багов этапа.
- **Счётчик абонемента показывает будущее.** Сегменты сверх будущего
  остатка, но в пределах текущего, штрихуются красным: видно, что именно
  спишется, до нажатия «Сохранить».
- **Групповое занятие** — блок на каждого участника со своими шестью
  отметками и своим предпросмотром. `POST` уходит по одному на ученика
  и последовательно: при ошибке на втором важно знать, что первый уже записан.
- **Клавиатура.** `Esc` закрывает панель, цифры `1`–`6` выбирают отметку,
  когда неотмеченный участник один — самый частый случай на ресепшене.
  Если открыт вопрос об отмене отметки, первый `Esc` снимает его, а не
  закрывает панель: рефлекторное «нет» не должно стоить открытой карточки.
- **Отмена отметки — в блоке участника, а не в подвале панели.** Подвал
  относится к занятию целиком, а отменяют всегда одного человека: на группе
  из четырёх это разница между «исправил» и «сломал». Кнопка появляется
  только у отмеченного участника и только когда пришёл `attendance_id` —
  без него вызывать `DELETE` нечем, и неработающей кнопки быть не должно.
  Подтверждение показывает, что именно вернётся: занятие на абонемент
  (счётчик тут же дорисовывает возвращаемый сегмент), снятое начисление
  преподавателю и отозванная отработка. После ответа те же числа
  повторяются уведомлением — уже цифрами сервера.
- **После отмены панель остаётся открытой.** Ошибочную отметку почти всегда
  сразу заменяют правильной; закрывать панель значило бы заставить искать
  занятие в расписании заново. Расписание при этом перечитывается: занятие
  без единой отметки снова становится запланированным.

Обязательные состояния: скелет загрузки формой дорожек, пустой день,
ошибка с текстом `message` от сервера и кнопкой «Повторить», ошибка
сохранения — прямо в панели, над кнопками.

Решения этапа 2:

- **Поиск — по родителю, а не только по ребёнку.** Телефон плательщика
  стоит прямо в строке результата: перезвонить можно, не открывая карточку.
  Запрос отстаёт от ввода на 250 мс и уходит от двух символов.
- **Карточка идёт в порядке вопросов на ресепшене**: сколько занятий
  осталось → что говорил преподаватель → куда делись занятия. Справа —
  то, что нужно для разговора с родителем: кто платит, по каким правилам,
  какой риск не продлить.
- **Счётчик абонемента тот же, что в панели отметки** — сегментами.
  Число занятий читается, а не оценивается на глаз; в диалоге заморозки
  тем же счётчиком показан годовой лимит дней, где использованные дни
  сплошные, а выбранные сейчас — штриховкой.
- **Предпросмотр продажи и заморозки** — главный приём этапа: сколько
  занятий, до какого числа, сколько к оплате, сколько занятий отменится.
  В отличие от отметки, эти числа считает клиент: эндпоинтов предпросмотра
  контракт не даёт (см. пробелы 9 и 10). Всё, чего клиент знать не может —
  промокод и точное число отменённых занятий, — помечено как «проверит
  сервер», а после ответа итог показывается ещё раз, уже числами сервера.
- **Опасные операции блокируются до отправки.** Продажа внутрь
  действующего периода, заморозка в прошлом и заморозка сверх лимита
  гасят кнопку и объясняют причину. Всё остальное решает сервер:
  пересечение заморозок и промокод возвращаются ошибкой и показываются
  её текстом.
- **Два клика в блоке занятия.** Клик по блоку открывает отметку — самое
  частое действие смены; клик по имени ведёт в карточку ученика.
  Кнопка внутри кнопки недопустима, поэтому область отметки — отдельная
  кнопка на весь блок, а имя лежит поверх неё. Из панели отметки имя
  участника ведёт туда же.
- **Модальное окно, а не боковая панель.** Продажа требует
  сосредоточенности и не должна соседствовать с расписанием, по которому
  легко случайно кликнуть. `Esc` и клик по фону закрывают.

Решения этапа 3:

- **Доска — очередь работы, а не список.** Внутри колонки сверху то, что
  ждёт дольше всех; флаги (`не дозвонились`, `просрочено`, `пробный сегодня`,
  `кабинет занят`) стоят на карточке, чтобы смотреть на доску, а не
  перечитывать заявки.
- **Перетаскивание применяется сразу и откатывается при отказе.** Карточка
  переносится в локальной копии доски до ответа сервера; если `PATCH`
  вернул ошибку, копия возвращается к снимку, а текст сервера уходит
  в уведомление. Показанная стадия обязана совпадать с той, что в базе.
  Запасной путь есть всегда: стадия меняется и списком в карточке.
- **Два перехода интерфейс не пускает молча.** «Абонемент куплен» вручную
  не ставится — это делает конверсия; «Отказ» требует причину, поэтому
  при перетаскивании в эту колонку интерфейс сначала спрашивает её,
  а уже потом отправляет запрос.
- **Занятость слота видна до отправки.** В диалоге пробного под формой
  стоят занятия выбранного преподавателя и кабинета на этот день,
  пересечение подсвечивается. Но решает сервер: его `409` — не ошибка,
  а вопрос «поставить всё равно», и кнопка отправляет тот же запрос
  с `overbook_ack: true`.
- **Предпросмотр продажи один на два экрана.** Конверсия и продажа
  из карточки ученика используют один компонент (`students/planPreview.tsx`):
  разные формулы в двух диалогах — это разные суммы, названные родителю.
- **Возраст ниже минимального — предупреждение, а не запрет.** Порог
  приходит с сервера в направлении заявки; решение оставлено администратору,
  как и требует контракт.
- **Смещение пояса не пишется цифрой.** Время пробного собирается в ISO
  со смещением, взятым из строк расписания филиала: захардкоженный `+06`
  однажды сдвинет все пробные на час.

Решения этапа 4:

- **Сводка отвечает на вопросы владельца по порядку**: сколько заработали →
  куда упёрлись → сколько отдать → к кому идти. Четыре карточки шапки
  и блок «требует внимания» видны на всех вкладках: закрытие периода
  не должно уводить с экрана, где стоят долги и кончающиеся абонементы.
- **`carried_over` — отдельная колонка, а не поправка к сумме.** Правки
  за уже закрытые месяцы приезжают в текущую ведомость, и без своей колонки
  бухгалтер искал бы, почему итог не сходится с занятиями месяца.
  Под таблицей стоит объяснение, в расшифровке такие строки помечены плашкой
  «прошлый месяц» и подсвечены латунным фоном.
- **Занятия и начисления — две колонки.** У группы из четырёх человек занятие
  одно, а начислений четыре; одна колонка «занятий» врала бы в обе стороны.
- **Ставка со флажком `±`.** `rate` — самая частая сумма начисления, и когда
  `rate_varies`, рядом стоит знак: показывать одно число, когда ставок
  несколько, значит вводить в заблуждение.
- **Закрытие периода спрашивает трижды.** Диалог показывает, что именно
  закрывается (начислений, преподавателей, занятий, сумма, в том числе правки
  и строки из прошлых месяцев), предупреждает о необратимости **до** кнопки,
  а не уведомлением после, и требует галочку с суммой прописью действия.
  Незакончившийся период гасит кнопку и объясняет причину до отправки —
  сервер ответил бы `422`, но условие проверяемо на клиенте. Итог показывается
  формулировкой сервера: числа в ней уже посчитаны, пересказывать их
  своими словами значило бы завести второй источник правды.
- **Отток не выводится, но место под него занято.** Бэкенд считает отток
  по абонементам, а не по ученикам, и завышает его в разы (#25). Показать
  такое число хуже, чем не показать: на него начнут принимать решения.
  Убрать карточку тоже нельзя — о дырке забыли бы. Поэтому карточка стоит
  на месте пунктиром, с прочерком вместо числа и объяснением, что чинится.
  Поле `churn` при этом описано в типах: когда бэкенд починится, менять
  придётся один компонент.
- **Филиал переключается внутри экрана, а не в верхней панели.** У отчётов
  есть режим «все филиалы», которого нет ни у расписания, ни у воронки:
  занятие всегда происходит в конкретном филиале, а выручка школы — нет.
- **Долги живут без периода.** Долг — состояние на сейчас, а не сумма
  за отрезок, и переключатель периода на этот отчёт не влияет. Об этом
  сказано прямо на карточке: смена месяца без изменения цифр иначе выглядит
  как поломка. Если сервер отдал не всех должников (`limit`), в заголовке
  таблицы стоит «N самых крупных из M».
- **Сумма разрезов выручки показана явно.** Строка «Сумма разрезов» под
  каждым разрезом сходится с итогом и зеленеет; расхождение стало бы видно
  сразу. Платёж без абонемента попадает в «Не распределено» — иначе разрезы
  не сошлись бы, а несходящийся финансовый отчёт хуже отсутствующего.
- **Процент загрузки не показывается без базы.** Под числом стоит
  `capacity_note` сервера с формулой ёмкости и часы «занято из».
- **Расшифровка ведомости — по требованию, а не сразу.** Строка раскрывается
  кликом по имени, и только тогда уходит запрос: у десяти преподавателей
  это десять лишних запросов при каждом открытии экрана.

## Пробелы контракта и как они закрыты

1. **Правило отметки `cancelled_late` нигде не описано.** В `spec.md`
   таблица правил её не содержит, контракт только вводит ключ.
   В моках приравнена к прогулу: списывается занятие, преподавателю 100%.
   Настоящее правило считает бэкенд — интерфейс показывает то, что придёт.
2. **`attendance_mark` у группового занятия.** В расписании поле одно,
   а участников несколько. Мок отдаёт отметку первого отмеченного участника.
   Нужно решение: либо агрегат (`held`/`partial`), либо счётчик отмеченных.
3. **`GET /lessons/{id}` не содержит заголовка занятия и филиала.**
   В расписании `title` есть, в карточке — нет. Заголовок панели собирается
   из имён участников (`Группа · 4 чел.` при трёх и более).
4. **`status` после отметки всегда `held`,** включая отмену занятия.
   Контракт говорит «занятие получает `status = held` после первой отметки»,
   но отменённое занятие проведённым не было. Интерфейс поэтому опирается
   на `attendance_mark`, а не на `status`.
5. **`DELETE /attendance/{id}` описан без тела ответа.** ~~Отмена не
   реализована~~ — **закрыто** (задача #10). Бэкенд добавил `attendance_id`
   в `participants[]`, и кнопка отмены появилась. Тело ответа контракт
   по-прежнему не задаёт, поэтому тип `AttendanceRevokeResponse` списан
   с реализации (`schemas.AttendanceRevoked`): `attendance_id`, `mark`,
   `revoked_at`, `reverted` и `lesson_status`. Выдуманная «по аналогии»
   структура молча разошлась бы с сервером на первом же вызове. **Эти пять
   ключей нужно внести в контракт словами.**
   Остаётся два хвоста:
   - **предпросмотра отмены нет** — эндпоинта, который скажет, что вернётся,
     контракт не даёт. Показываем зеркало применённого эффекта: дельты
     из `mark_effects` с обратным знаком плюс текущий остаток абонемента.
     Это не расчёт правил на клиенте, а разворот знака у серверных чисел;
     точные значения приходят в ответе и повторяются уведомлением — тот же
     приём, что у продажи и заморозки (пробелы 9 и 10);
   - ~~**`mark_effects` у уже отмеченного участника считается от текущего
     остатка**~~ — **закрыто** (issue #22, этап 4). Бэкенд добавил
     `applied_effect` в участника карточки занятия: факт из журнала, а не
     пересчёт правил. Обход, подставлявший вместо `lessons_after` остаток
     абонемента, снят — блок «Отмечено» показывает серверные числа целиком,
     включая `summary`. Ключа нет ни в одном контракте: тип
     `AppliedMarkEffect` списан с реализации (`schemas.AppliedEffect`),
     **его нужно внести в контракт словами**. Поле объявлено необязательным:
     старый бэкенд его не отдаёт, и тогда блок покажет только саму отметку,
     но ничего не соврёт.
6. **Предпросмотр при нулевом остатке.** Контракт описывает `422` при
   списании с пустого абонемента, но не говорит, как выглядит `mark_effects`
   в этом случае. Мок отдаёт `lessons_delta: -1`, `lessons_after: 0`
   и предупреждающий `summary`; интерфейс подсвечивает такой предпросмотр
   красным, но кнопку не блокирует — решение об отказе принимает сервер.
7. **`branch` в ответе расписания без `timezone`,** в `GET /branches` — с ним.
   Расхождение сохранено в типах как есть; смещение берётся из ISO-строк.
8. **Нет эндпоинта «сегодня» и часового пояса школы.** Дата по умолчанию —
   локальная дата браузера (в мок-режиме — 12 августа 2026, день прототипа).
   Вынесено в `src/lib/today.ts`, чтобы «сегодня» было одно на все экраны.

Этап 2:

9. **Нет предпросмотра продажи.** Контракт требует показать итог до
   подтверждения, но эндпоинта, который его посчитает, не даёт. Итог
   считается на клиенте из полей тарифа (`lessons_count`, `valid_days`,
   `price`) и введённой скидки — это чистая арифметика по данным сервера.
   Промокод в неё не входит: клиент не знает ни списка кодов, ни их действия,
   поэтому промокод помечен как «проверит сервер», а после ответа сумма
   показывается заново из `charged`. Правильное решение —
   `POST /students/{id}/subscriptions/preview` с телом продажи и тем же
   ответом, что у продажи: тогда клиент перестанет считать деньги вовсе.
10. **Нет предпросмотра заморозки.** «Сколько занятий будет отменено»
    известно только серверу — расписания на месяцы вперёд у клиента нет.
    Показываем оценку по темпу абонемента (занятий на день × дней заморозки)
    с пометкой «ориентировочно»; на примере из контракта (11 дней, абонемент
    8 занятий на 31 день) оценка даёт ровно 3 занятия, как в контракте.
    Точное число приходит в ответе и показывается в уведомлении. Нужен
    предпросмотр либо список ближайших занятий ученика в карточке.
11. **`valid_until` при продаже.** Контракт даёт пример: `starts_on`
    1 сентября, `valid_days` 31 → `valid_until` 1 октября. Значит, последний
    день включительно (`starts_on + valid_days − 1`), а не «плюс 31 день».
    Так же считает и мок. Формулу стоит записать в контракт словами.
12. **Фильтр тарифов по направлению не применить.** `GET /plans` принимает
    `discipline_id`, а карточка ученика отдаёт только название направления
    (`"discipline": "Барабаны"`). Тарифы запрашиваются целиком, а тарифы
    направления ученика поднимаются наверх списка на клиенте. Нужен либо
    `discipline_id` в карточке, либо фильтр по имени в `/plans`.
13. **`carry_over_lessons` есть в описании продажи, но нет в `rules`
    карточки.** Ключ объявлен необязательным в типе `SubscriptionRules`;
    когда он приходит, интерфейс показывает строку «Перенос остатка»
    и разрешает галочку переноса, иначе прячет её смысл за подписью
    «правило школы — перенос запрещён». Ключ стоит добавить в пример
    карточки: без него интерфейс не знает, предлагать перенос или нет.
14. **`DELETE .../holds/{hold_id}` описан без тела ответа.** Тип
    `HoldReleaseResponse` объявлен с необязательными полями по аналогии
    с `POST`; интерфейс показывает `valid_until_after` и `lessons_cancelled`,
    если они пришли.
15. **Формат интервала заморозки.** Контракт даёт `from` 14 августа,
    `to` 25 августа и `days: 11` — значит, `to` не входит в интервал
    (полуинтервал, как `daterange` в базе). В диалоге поле подписано
    «По какой (не включая)», чтобы администратор не ошибся на день.
16. **`payer` в поиске и в семье.** Контракт показывает плательщика
    всегда, но у взрослого ученика семьи может не быть. В типах поле
    допускает `null`: строка поиска без телефона полезнее упавшего экрана.
17. **Нет эндпоинта ближайших занятий ученика.** Из-за этого в карточке
    нет блока «следующие занятия», а предупреждение об отменённых занятиях
    при заморозке приблизительное (см. пробел 10).

Этап 3:

18. **Нет справочников преподавателей, кабинетов и направлений.** Клиент
    к ним **готов** (задача #1): `api.teachers(branch_id)`, `api.rooms(branch_id)`,
    `api.disciplines()` описаны в типах и вызываются; моки их отдают.
    Формы справочника нет в контрактах, поэтому типы `DirectoryTeacher`,
    `DirectoryRoom` и `Discipline` собраны по задаче #1 и по схеме базы,
    а всё, чего задача не гарантирует явно, объявлено необязательным.
    Основной источник теперь справочник, запасной — расписание:
    - **диалог пробного** берёт преподавателей и кабинеты из `GET /teachers`
      и `GET /rooms`; если справочник ответил ошибкой или пуст, списки
      по-прежнему собираются из `GET /schedule` (выбранный день плюс
      сегодняшний), но под формой встаёт строка о том, что это срез дня,
      а не справочник, — иначе пропавший преподаватель выглядит как «уволен»;
    - **форма заявки** показывает выбор направления, когда `GET /disciplines`
      ответил. Пустой выпадающий список читался бы как «направлений в школе
      нет», поэтому без справочника поля просто не будет и заявка создастся
      без направления — как и раньше.

    На живом бэкенде все три эндпоинта пока отвечают `404`, и интерфейс
    работает запасным путём. Когда они появятся, менять код не придётся.
19. **`min_age` направления нет в ответе.** Контракт требует сверять
    возраст с минимальным для направления, но `GET /leads/{id}` отдаёт
    только `{id, name}`. Поле объявлено необязательным в типе
    `LeadDiscipline`; мок его присылает, и предупреждение работает.
    Без него интерфейс просто промолчит — жёстко зашивать пороги
    на клиенте нельзя, они у каждой школы свои.
20. **Форма `trial` на доске не описана.** В карточке пробный расписан
    полностью, на доске назван «кратким описанием». Держим одну структуру
    `LeadTrial` с необязательными `status` и `conflicts`: доска
    показывает время, преподавателя и флаг конфликта из тех же полей.
21. **Стадия `trial_booked` вручную.** Контракт разрешает менять стадию
    через `PATCH`, но стадия «пробный назначен» означает занятие
    в расписании. Мок отвечает `422` с указанием нажать «Назначить
    пробный»; если бэкенд решит иначе, интерфейс покажет то, что придёт.
22. **`comment` принимается в `POST /leads`, но не возвращается.** Поле
    объявлено необязательным в `LeadCard` и показывается, когда приходит:
    комментарий «удобно после 18:00» — половина смысла заявки.
23. **`birth_date` при конверсии.** Контракт ждёт дату рождения, а в заявке
    есть только возраст. Поле оставлено пустым и необязательным, рядом
    показан возраст из заявки: выдумывать дату из возраста нельзя —
    она попадёт в базу как факт.
24. **Вебхук `POST /hooks/leads` — не фронтендовый.** Ключи `X-Api-Key`
    интерфейсу не выдаются, экрана управления ключами контракт
    не предусматривает; заявки из внешних источников просто появляются
    на доске с нужным `source`.

Этап 4:

25. **Форм отчётов в контракте нет — только описание словами.** Контракт
    подробно задаёт ведомость, расшифровку, список периодов и закрытие,
    а четыре отчёта (`revenue`, `rooms`, `debts`, `summary`) описывает
    прозой: «разрезы по филиалам, направлениям, месяцам и способам оплаты».
    Типы `RevenueReport`, `RoomsReport`, `DebtsReport` и `MoneySummary`
    сняты с работающего API и сверены со схемами бэкенда
    (`schemas.Revenue`, `RoomsReport`, `DebtsReport`, `MoneySummary`).
    **Их нужно внести в контракт формами, а не описанием.**
26. **`branch_id` есть в ответах, но не в контракте.** Ведомость, выручка,
    загрузка и сводка возвращают выбранный филиал эхом. Поле объявлено
    необязательным и не используется интерфейсом — фильтр он и так знает, —
    но в типе оставлено, чтобы расхождение было заметно.
27. **Форма `calc` не закреплена.** Контракт даёт пример
    `{kind, mark, rate, share, amount}` и называет его «снимком расчёта»,
    но состав ключей не фиксирует, и у премии он будет другим. Тип
    `PayrollCalc` объявлен со всеми известными ключами необязательными
    плюс индексная сигнатура; интерфейс читает `rate` и `share`, а о том,
    чего не знает, молчит — падать на чужом ключе снимок не должен.
28. **`MoneySummary.churn` описан, но не выводится** — см. #25 бэкенда
    и решение про заглушку выше.
29. **`mark_effects` подрос сверх контракта.** В ответе живого бэкенда
    у эффекта отметки есть `makeups_after` и `blocked_reason`, которых нет
    ни в контракте, ни в типе `MarkEffect`. Интерфейс их не использует
    (лишние ключи в JSON типам не мешают), но `blocked_reason` выглядит
    как готовый ответ на вопрос «почему кнопка не сработает» —
    **стоит описать его в контракте и показать в панели отметки.**
30. **`GET /reports/debts` ограничен `limit`, а `families` считает всех.**
    Расхождение честное, но требует объяснения: заголовок таблицы
    показывает «50 самых крупных из 62», когда список обрезан. Полного
    списка должников с постраничностью контракт не даёт.
31. **«Сегодня» по-прежнему берётся из браузера** (см. пробел 8), и на нём
    же держится проверка «период ещё не закончился». Эндпоинт «сегодня
    по времени школы» закрыл бы сразу оба места: сейчас администратор
    с неверно выставленными часами увидит кнопку закрытия на день раньше,
    а сервер всё равно ответит `422`.

Этап 5:

32. **`429` не говорит, сколько ждать.** Заголовка `Retry-After` в ответе нет,
    а во всех четырёх формулировках сервера названо одно окно — четверть часа
    (`auth.ATTEMPT_WINDOW`). Оно зашито константой `LOCK_MS` в `LoginScreen`
    и держит выключенными и отправку, и «выслать заново». Число на клиенте,
    повторяющее число на сервере, разъедется при первой правке настроек:
    **`Retry-After` или `retry_after` в `details` закрыли бы это точно.**
33. **Ответ входа содержит `token`, и фронтенду он не нужен.** Кука ставится
    тем же ответом. Поле объявлено необязательным в типе `LoggedIn` и нигде
    не читается — класть его в `localStorage` нельзя, весь смысл `HttpOnly`
    в том, что там его нет.
34. ~~**Кабинета родителя как экрана нет.**~~ — **закрыто контрактом этапа 5.**
    Собственных ресурсов у кабинета не существовало: `GET /schedule` отдаёт
    сетку филиала и родителю закрыт, а расписание своего ребёнка читалось
    только поштучно через `GET /lessons/{id}` (issue #5 бэкенда). Контракт
    ответил на это не параметром к общему расписанию, а отдельным
    `GET /me/schedule`, и это правильнее: урезание общего ресурса — операция
    вычитания, и ошибается она молча и в сторону утечки. Кабинет собран
    по `/me/*` целиком.
35. **Смены пароля и управления устройствами в интерфейсе нет.** Эндпоинтов
    тоже: пароль проставляется посевом, а «мои устройства» существует только
    как `POST /auth/logout?everywhere=true` вслепую. Экран профиля со списком
    сессий однажды спросят — в этап он не входил.

Кабинет родителя (`docs/contract-v5.md`):

36. **Контактов школы нет ни в одном контракте.** Кабинет обязан показывать
    телефон и WhatsApp — оплаты в нём нет намеренно, и без контактов он ведёт
    в тупик, — но взять их неоткуда: `GET /auth/me` отдаёт у тенанта только
    `id` и `name`. В типе `TenantRef` заведено необязательное поле `contacts`
    (`phone`, `whatsapp`), мок его отдаёт; на живом бэкенде работает запасной
    вариант из `VITE_SCHOOL_PHONE` и `VITE_SCHOOL_WHATSAPP`. **Это временно
    и неправильно**: в мультитенантном продукте телефон школы не может лежать
    в сборке фронтенда — один бандл обслуживает все школы, и все получат один
    номер. Поле нужно в `tenant` ответа `/auth/me`.
37. **Форма ответа `renew-request` не задана.** Контракт говорит «`201`
    с задачей администратору» и не показывает тела. Тип `RenewCreated` объявлен
    с обязательным `message` и необязательными `request_id` и `status`:
    интерфейс показывает текст сервера и ничего не выдумывает. Повторная заявка
    на продление в моках разрешена — `409` контракт задаёт только для переноса,
    и выдумывать второй отказ там, где сервер, возможно, его не даёт, нельзя.
38. **`starts_at` в истории есть не всегда.** Контракт показывает его у каждой
    записи, но история — это движения абонемента, и у части из них занятия
    в фикстурах нет (заметка за день, оплаченный прошлым абонементом). Поле
    объявлено `string | null`; интерфейс тогда показывает только дату.
    Заодно: контракт не говорит, попадают ли в `history` покупка и продление.
    Сейчас в кабинете их нет — это «история посещений», а не журнал.
39. **`GET /me/children` не отдаёт `can_request_reschedule`.** Флаг есть
    у занятия в расписании, но не у `next_lesson`, а кнопка «попросить
    о переносе» нужна и на главном экране — там она и стоит. Прятать её
    по клиентской догадке нельзя: порог отмены — правило школы. Поэтому кнопка
    показывается всегда, а отказ приходит текстом сервера прямо в форму заявки
    (`422` называет порог и что делать вместо). В карточке занятия, где флаг
    есть, кнопка гасится по нему — там догадка не нужна. **Флаг стоит добавить
    в `next_lesson`.**
40. **Порядок `history` не задан.** Контракт даёт пример из одной записи.
    Кабинет показывает от новых к старым: последнее занятие — то, о котором
    спрашивают вечером.
41. **Бэкенд отдаёт больше, чем описывает контракт, и это хорошо.** Формы
    сверены с реализацией (`backend/app/schemas.py`), и три ключа сверх
    контракта уже используются — **их нужно внести в контракт словами**:
    - `FamilyLesson.reschedule_request` (`{request_id, status}` или `null`) —
      заявка приезжает вместе с занятием. Без него «заявка отправлена» жило бы
      только в памяти вкладки: после перезагрузки родитель увидел бы кнопку
      снова, нажал и получил `409`, то есть решил бы, что первая потерялась.
      Теперь состояние видно и в списке недели плашкой «Просили перенос»;
    - `FamilyHistoryRow.title` — формулировка движения из журнала абонемента.
      Показывается **только там, где отметки нет**: рядом с отметкой она
      дублирует её словами регламента, и «Прогул без предупреждения» под
      мягким «Не пришёл» звучит как второй, настоящий приговор;
    - `FamilyHistoryRow.makeups_delta` — начисленная отработка в той же строке.

    Заодно расхождение в другую сторону: у бэкенда `age`, `discipline`
    и `teacher` допускают `null`, а контракт показывает их заполненными.
    В типах они `| null`, и подписи собираются `joinDot`, чтобы пустое поле
    не оставляло висящую точку («· Дмитрий Шарапов» читается как поломка).

## Закрытый долг

- **Отмена ошибочной отметки** (задача #10). Кнопка «Отменить отметку»
  стоит в блоке отмеченного участника, подтверждение показывает, что
  вернётся, после ответа расписание и панель перечитываются. Интерфейс
  рассчитан на состояние **после** исправления уникального индекса
  (задача #2 бэкенда): отменённый участник снова доступен для отметки,
  и мок ведёт себя именно так. Пока индекс не поправлен, живой сервер
  на повторную отметку отвечает `409 mark_revoked` — интерфейс покажет
  его текст в блоке участника и ничего не сломает.
- **Подготовка к справочникам** (задача #1) — см. пробел 18.
- **Обход в панели отметки снят** (issue #22). `applied_effect` заменил
  подстановку остатка абонемента вместо `lessons_after`; клиентских правок
  серверных чисел в панели больше нет — см. пробел 5.
