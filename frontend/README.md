# RockCRM — фронтенд, этапы 1–3

**Этап 1** (`docs/contract-v1.md`): расписание филиала на день и панель
отметки посещаемости с предпросмотром последствий.

**Этап 2** (`docs/contract-v2.md`): экран «Ученики» с поиском по родителю,
карточка ученика, продажа и продление абонемента, заморозка. У продажи
и заморозки — предпросмотр итога до подтверждения, тот же принцип,
что и у отметки.

**Этап 3** (`docs/contract-v3.md`): воронка заявок — доска по стадиям
с перетаскиванием и откатом при отказе сервера, карточка заявки,
назначение пробного урока с видимой занятостью и подтверждением
овербукинга, конверсия в ученика с продажей абонемента и отчёт
по воронке.

Визуальный ориентир — `prototype/index.html`.

> В репозитории может лежать `.env.development.local` с `VITE_USE_MOCKS=false`
> — переключение на живой бэкенд. Эндпоинтов свежего этапа там может ещё
> не быть: чтобы посмотреть новые экраны, поставьте в этом файле `true`
> или удалите его.

## Как запустить

```bash
cd frontend
npm install
npm run dev          # http://localhost:5173
```

По умолчанию dev-сервер стартует **на моках**: значения лежат
в `.env.development`, бэкенд не нужен.

Другие команды:

```bash
npm run build        # проверка типов + продакшен-сборка
npx tsc --noEmit     # только проверка типов
```

## Мок-режим

Включается переменной окружения `VITE_USE_MOCKS`.

| Переменная | Смысл |
|---|---|
| `VITE_USE_MOCKS` | `true` — данные из мок-сервера, `false` — запросы к бэкенду |
| `VITE_API_BASE_URL` | базовый путь API, по умолчанию `/api/v1` |
| `VITE_PROXY_TARGET` | куда dev-сервер проксирует `/api`, по умолчанию `http://127.0.0.1:8000` |
| `VITE_TENANT_ID`, `VITE_USER_ID` | заглушка авторизации из контракта, уходит в заголовки `X-Tenant-Id` и `X-User-Id` |
| `VITE_MOCK_LATENCY_MS` | задержка мок-ответов, чтобы состояние загрузки было видно |

Работа против настоящего бэкенда:

```bash
# .env.development.local — именно так, не .env.local
VITE_USE_MOCKS=false
VITE_PROXY_TARGET=http://127.0.0.1:8000
```

Файл обязан быть `.env.development.local`. В Vite режимный файл
`.env.development` перебивает `.env.local`, поэтому переключение через
`.env.local` молча не сработает: интерфейс останется на моках,
и это выглядит как «всё работает», пока не заметишь, что данные
не меняются после пересева базы.

Демо-данные бэкенда лежат на **12 августа 2026**, а интерфейс открывается
на сегодняшней дате и берёт первый филиал по алфавиту. На живом API
переключите дату и выберите «Аль-Фараби 53В», иначе увидите пустой день —
это не ошибка, там действительно нет занятий.

### Что в моках

`src/api/mocks/data.ts` повторяет день из прототипа: **12 августа 2026**,
филиал «Аль-Фараби 53В», те же преподаватели (Шарапов, Федько, Мадратов,
Меренков, Исенова) и ученики (Амина Сагындык, Даниал Ким, Марк Ли и др.).
12 занятий, 1 пробный, 1 конфликт кабинета — «Барабанная A» занята
Ержаном Оспановым 12:30–13:25 и пробным Алисы Ким 13:00–13:45.

Дни для проверки состояний:

- **12 августа** — рабочий день: планируемые, проведённое, прогул, пробный, группа;
- **11 августа** — день уже отмечен целиком (панель показывает применённые последствия);
- **13 августа и далее** — пустой день;
- **филиал «Абая 124»** — свой набор занятий.

Особые случаи в данных:

- **Дмитрий Со, 20:00** — на абонементе 0 занятий: предпросмотр предупреждает,
  `POST` возвращает `422` с текстом сервера;
- **Ансамбль «Пятый лад», 17:30** — групповое занятие, четыре участника,
  у каждого свои эффекты и своя отметка;
- **Алиса Ким (пробный)** и **Дамир Ералы** — без абонемента, занятие идёт
  разовой оплатой;
- **Мадина Абишева (2 занятия), Амир Жанат (2), Ержан Оспанов (1)** —
  после списания остаток ≤ 2 и приходит `alerts` о продлении.

Мок-сервер держит состояние в памяти вкладки: отметка меняет остаток
абонемента и статус занятия, повторная отметка того же ученика даёт `409`.
Перезагрузка страницы возвращает исходный день.

**Отмена отметки** (`DELETE /attendance/{id}`) возвращает занятие на абонемент,
снимает начисление преподавателю и снимает саму отметку — после неё ученик
снова доступен для отметки, и мок это разрешает (см. «Отмена отметки» ниже).
Отметки из фикстур — день **11 августа** — тоже получают `attendance_id`,
поэтому кнопка отмены есть и там. Повторная отмена той же отметки даёт `409`.

### Данные этапа 2

Ученики из расписания дополнены профилем (возраст, направление, филиал,
семья), к ним добавлены семьи, тарифы, журнал абонемента, заметки
и отработки. Продажа и заморозка меняют состояние: новый абонемент виден
и в карточке, и в расписании — остаток берётся из одного объекта.

Сценарии для проверки:

- **Амина Сагындык** — карточка из прототипа: семья Сагындык, плательщик
  Гульнара `+77015550003`, скидка 10%, второй ребёнок Тимур (гитара),
  абонемент «Барабаны, 2 раза в неделю, 55 мин» 5 из 8, отработка до
  1 сентября, журнал из пяти движений, три заметки, риск оттока «Средний».
- **Поиск по родителю** — «Гульнара» и `5550003` находят обоих детей.
  Телефон ищется по цифрам, поэтому `+7 701 555 00 03`, `87015550003`
  и `5550003` дают один результат.
- **Продажа**: дата начала подставляется как следующий день после конца
  текущего абонемента — это единственный вариант без `422`. Дата внутри
  действующего периода блокируется ещё в предпросмотре.
- **Промокод**: `RS25` даёт дополнительные 5% (итог 45 900 ₸ при скидке
  семьи 10%), любой другой код — `422` с текстом сервера.
- **Оплата**: снятая галочка «деньги приняты» оформляет абонемент в долг,
  долг попадает в блок семьи.
- **Заморозка**: 14–25 августа — ровно пример контракта: 11 дней,
  срок сдвигается на 11 дней, отменяется ≈3 занятия, лимита остаётся 3.
  Повтор с пересекающимся интервалом даёт `409`, интервал длиннее остатка
  лимита и дата в прошлом блокируются до отправки.
- **Алиса Ким** — ученик без абонемента, семьи, заметок и журнала: все
  пустые состояния карточки видны на одном экране.
- **Семья Абишевых** — долг 27 000 ₸ в блоке семьи.

### Данные этапа 3

Воронка повторяет доску из прототипа: 15 заявок на всех стадиях, разные
источники, три отказа с причинами и пробный в занятом кабинете. Заявки
связаны с расписанием: пробные Алисы Ким и Ильяса Абена — те самые занятия
12 августа, и конфликт «Барабанной A» виден и на доске, и в расписании.

Сценарии для проверки:

- **Алиса Ким** (пробный назначен) — два флага сразу: «пробный сегодня»
  и «кабинет занят»; в карточке видно, чем именно занят слот.
- **Мадина Абишева** (новая) — «не дозвонились ×2» и просроченное
  напоминание: обе причины дёрнуть заявку видны прямо на доске.
- **Аяна Досым, 4 года, барабаны** — возраст ниже минимального (с 5 лет):
  карточка предупреждает, но ничего не запрещает.
- **Назначение пробного**: «Класс 1» для барабанов даёт `422` (нет
  установки), «Барабанная A» на 13:00 — `409` с предложением подтвердить
  овербукинг; после подтверждения занятие появляется в расписании
  с пометкой конфликта.
- **Перетаскивание**: в «Абонемент куплен» вручную нельзя — `422`, карточка
  возвращается назад; в «Отказ» интерфейс сначала спрашивает причину.
- **Конверсия**: у заявки «Айгуль Бек / Алихан» телефон совпадает
  с плательщиком существующей семьи — сервер переиспользует её, и в карточке
  ученика появляются оба ребёнка.
- **Дубль заявки**: заведите вручную заявку на `+7 701 555 00 09` — придёт
  `409` со ссылкой на существующую.
- **Отчёт по воронке** — период по умолчанию месяц; демо-данные лежат
  на июль–август 2026.

## Решения по стеку

**React 18 + TypeScript + Vite** — задано контрактом.

**Никакой библиотеки состояния.** Состояние приложения — выбранный филиал,
дата, открытое занятие, открытый экран и строка поиска. Кэш между экранами
не нужен: карточка ученика после продажи обязана перечитаться, а не
показать сохранённое. Redux/Zustand добавили бы слой без задачи. Загрузка
данных вынесена в `src/lib/useAsync.ts` (30 строк): состояния
`loading/error/data`, ручной `reload` и отбрасывание ответов на устаревшие
запросы по счётчику поколений — на поиске с задержкой ввода это как раз
и нужно. TanStack Query станет осмысленным, когда появится общий кэш
между экранами денег и учеников.

**Никакого роутера.** Экрана два с половиной, ссылками на карточку
пока не делятся, `react-router` добавил бы зависимость ради одного `switch`.
Экран хранится состоянием, «Назад» из карточки возвращает туда, откуда
пришли, — в расписание или в поиск. Как только понадобится «отправь мне
ссылку на карточку», роутер станет оправдан.

**Обычный CSS с переменными, без препроцессоров и UI-китов.** Токены
прототипа (палитра, шрифты, тени) — это уже дизайн-система в CSS-переменных;
tailwind или styled-components заставили бы переписать их в третьей форме.
`src/styles/tokens.css` — токены и обе темы, `src/styles/app.css` — компоненты.
Классы и структура намеренно совпадают с прототипом (`.les`, `.track`,
`.rule`, `.pill`), чтобы правку из прототипа можно было перенести напрямую.

**Ноль рантайм-зависимостей, кроме react и react-dom.** Даты форматируются
вручную (`src/lib/format.ts`): нужны русские месяцы, сдвиг на день
и разбор ISO-строки — date-fns ради этого не нужен.

Зависимости зафиксированы точными версиями: `react`/`react-dom` 18.3.1,
`vite` 5.4.11, `typescript` 5.6.3, `@vitejs/plugin-react` 4.3.4.

## Устройство

```
src/
  api/
    types.ts          — граница с бэкендом: все формы ответов по контракту
    http.ts           — fetch, заголовки тенанта, разбор ошибки в ApiError
    index.ts          — выбор источника: моки или HTTP
    mocks/data.ts     — фикстуры: день из прототипа, семьи, тарифы, журнал,
                        направления, воронка заявок
    mocks/server.ts   — мок-сервер: правила отметки, конфликты, продажа,
                        заморозка, риск оттока, стадии заявок, воронка
  features/
    schedule/         — экран расписания и дорожки
    attendance/       — панель отметки
    students/         — поиск, карточка ученика, продажа, заморозка,
                        planPreview.tsx — общий предпросмотр абонемента
    leads/            — доска воронки, карточка заявки, пробный, конверсия,
                        отчёт по воронке
  components/         — состояния (загрузка/пусто/ошибка), уведомления, диалог
  lib/                — форматирование, загрузка данных, тема, «сегодня»
  styles/             — токены и стили
```

Ключевые решения интерфейса:

- **Расписание — многодорожечный секвенсор.** Дорожка = преподаватель,
  ось X = время, ширина блока = длительность. Конфликты и «дыры» в дне
  видно без чтения. Дорожка позиционируется в единицах `--hw` (ширина часа),
  поэтому масштаб меняется одной переменной.
- **Время не проходит через `Date`.** ISO-строка уже несёт смещение филиала;
  `new Date()` пересчитал бы её в пояс браузера, и администратор в Алматы
  увидел бы расписание по времени своего ноутбука. Часы и минуты берутся
  из строки регуляркой (`wallTime`, `wallMinutes`).
- **Фон занятия кодирует отметку, а не статус.** После отметки `status`
  у всех занятий становится `held`, а администратору важно, пришёл ученик
  или прогулял: зелёный — пришёл/опоздал, красный — прогул, серый —
  отменено, латунный — пробный.
- **Последствия не считаются на клиенте.** Панель показывает
  `mark_effects[отметка]` из `GET /lessons/{id}` дословно, включая
  `summary`. Клиентский расчёт разошёлся бы с сервером — это худший
  из возможных багов этапа.
- **Счётчик абонемента показывает будущее.** Сегменты сверх будущего
  остатка, но в пределах текущего, штрихуются красным: видно, что именно
  спишется, до нажатия «Сохранить».
- **Групповое занятие** — блок на каждого участника со своими шестью
  отметками и своим предпросмотром. `POST` уходит по одному на ученика
  и последовательно: при ошибке на втором важно знать, что первый уже записан.
- **Клавиатура.** `Esc` закрывает панель, цифры `1`–`6` выбирают отметку,
  когда неотмеченный участник один — самый частый случай на ресепшене.
  Если открыт вопрос об отмене отметки, первый `Esc` снимает его, а не
  закрывает панель: рефлекторное «нет» не должно стоить открытой карточки.
- **Отмена отметки — в блоке участника, а не в подвале панели.** Подвал
  относится к занятию целиком, а отменяют всегда одного человека: на группе
  из четырёх это разница между «исправил» и «сломал». Кнопка появляется
  только у отмеченного участника и только когда пришёл `attendance_id` —
  без него вызывать `DELETE` нечем, и неработающей кнопки быть не должно.
  Подтверждение показывает, что именно вернётся: занятие на абонемент
  (счётчик тут же дорисовывает возвращаемый сегмент), снятое начисление
  преподавателю и отозванная отработка. После ответа те же числа
  повторяются уведомлением — уже цифрами сервера.
- **После отмены панель остаётся открытой.** Ошибочную отметку почти всегда
  сразу заменяют правильной; закрывать панель значило бы заставить искать
  занятие в расписании заново. Расписание при этом перечитывается: занятие
  без единой отметки снова становится запланированным.

Обязательные состояния: скелет загрузки формой дорожек, пустой день,
ошибка с текстом `message` от сервера и кнопкой «Повторить», ошибка
сохранения — прямо в панели, над кнопками.

Решения этапа 2:

- **Поиск — по родителю, а не только по ребёнку.** Телефон плательщика
  стоит прямо в строке результата: перезвонить можно, не открывая карточку.
  Запрос отстаёт от ввода на 250 мс и уходит от двух символов.
- **Карточка идёт в порядке вопросов на ресепшене**: сколько занятий
  осталось → что говорил преподаватель → куда делись занятия. Справа —
  то, что нужно для разговора с родителем: кто платит, по каким правилам,
  какой риск не продлить.
- **Счётчик абонемента тот же, что в панели отметки** — сегментами.
  Число занятий читается, а не оценивается на глаз; в диалоге заморозки
  тем же счётчиком показан годовой лимит дней, где использованные дни
  сплошные, а выбранные сейчас — штриховкой.
- **Предпросмотр продажи и заморозки** — главный приём этапа: сколько
  занятий, до какого числа, сколько к оплате, сколько занятий отменится.
  В отличие от отметки, эти числа считает клиент: эндпоинтов предпросмотра
  контракт не даёт (см. пробелы 9 и 10). Всё, чего клиент знать не может —
  промокод и точное число отменённых занятий, — помечено как «проверит
  сервер», а после ответа итог показывается ещё раз, уже числами сервера.
- **Опасные операции блокируются до отправки.** Продажа внутрь
  действующего периода, заморозка в прошлом и заморозка сверх лимита
  гасят кнопку и объясняют причину. Всё остальное решает сервер:
  пересечение заморозок и промокод возвращаются ошибкой и показываются
  её текстом.
- **Два клика в блоке занятия.** Клик по блоку открывает отметку — самое
  частое действие смены; клик по имени ведёт в карточку ученика.
  Кнопка внутри кнопки недопустима, поэтому область отметки — отдельная
  кнопка на весь блок, а имя лежит поверх неё. Из панели отметки имя
  участника ведёт туда же.
- **Модальное окно, а не боковая панель.** Продажа требует
  сосредоточенности и не должна соседствовать с расписанием, по которому
  легко случайно кликнуть. `Esc` и клик по фону закрывают.

Решения этапа 3:

- **Доска — очередь работы, а не список.** Внутри колонки сверху то, что
  ждёт дольше всех; флаги (`не дозвонились`, `просрочено`, `пробный сегодня`,
  `кабинет занят`) стоят на карточке, чтобы смотреть на доску, а не
  перечитывать заявки.
- **Перетаскивание применяется сразу и откатывается при отказе.** Карточка
  переносится в локальной копии доски до ответа сервера; если `PATCH`
  вернул ошибку, копия возвращается к снимку, а текст сервера уходит
  в уведомление. Показанная стадия обязана совпадать с той, что в базе.
  Запасной путь есть всегда: стадия меняется и списком в карточке.
- **Два перехода интерфейс не пускает молча.** «Абонемент куплен» вручную
  не ставится — это делает конверсия; «Отказ» требует причину, поэтому
  при перетаскивании в эту колонку интерфейс сначала спрашивает её,
  а уже потом отправляет запрос.
- **Занятость слота видна до отправки.** В диалоге пробного под формой
  стоят занятия выбранного преподавателя и кабинета на этот день,
  пересечение подсвечивается. Но решает сервер: его `409` — не ошибка,
  а вопрос «поставить всё равно», и кнопка отправляет тот же запрос
  с `overbook_ack: true`.
- **Предпросмотр продажи один на два экрана.** Конверсия и продажа
  из карточки ученика используют один компонент (`students/planPreview.tsx`):
  разные формулы в двух диалогах — это разные суммы, названные родителю.
- **Возраст ниже минимального — предупреждение, а не запрет.** Порог
  приходит с сервера в направлении заявки; решение оставлено администратору,
  как и требует контракт.
- **Смещение пояса не пишется цифрой.** Время пробного собирается в ISO
  со смещением, взятым из строк расписания филиала: захардкоженный `+06`
  однажды сдвинет все пробные на час.

## Пробелы контракта и как они закрыты

1. **Правило отметки `cancelled_late` нигде не описано.** В `spec.md`
   таблица правил её не содержит, контракт только вводит ключ.
   В моках приравнена к прогулу: списывается занятие, преподавателю 100%.
   Настоящее правило считает бэкенд — интерфейс показывает то, что придёт.
2. **`attendance_mark` у группового занятия.** В расписании поле одно,
   а участников несколько. Мок отдаёт отметку первого отмеченного участника.
   Нужно решение: либо агрегат (`held`/`partial`), либо счётчик отмеченных.
3. **`GET /lessons/{id}` не содержит заголовка занятия и филиала.**
   В расписании `title` есть, в карточке — нет. Заголовок панели собирается
   из имён участников (`Группа · 4 чел.` при трёх и более).
4. **`status` после отметки всегда `held`,** включая отмену занятия.
   Контракт говорит «занятие получает `status = held` после первой отметки»,
   но отменённое занятие проведённым не было. Интерфейс поэтому опирается
   на `attendance_mark`, а не на `status`.
5. **`DELETE /attendance/{id}` описан без тела ответа.** ~~Отмена не
   реализована~~ — **закрыто** (задача #10). Бэкенд добавил `attendance_id`
   в `participants[]`, и кнопка отмены появилась. Тело ответа контракт
   по-прежнему не задаёт, поэтому тип `AttendanceRevokeResponse` списан
   с реализации (`schemas.AttendanceRevoked`): `attendance_id`, `mark`,
   `revoked_at`, `reverted` и `lesson_status`. Выдуманная «по аналогии»
   структура молча разошлась бы с сервером на первом же вызове. **Эти пять
   ключей нужно внести в контракт словами.**
   Остаётся два хвоста:
   - **предпросмотра отмены нет** — эндпоинта, который скажет, что вернётся,
     контракт не даёт. Показываем зеркало применённого эффекта: дельты
     из `mark_effects` с обратным знаком плюс текущий остаток абонемента.
     Это не расчёт правил на клиенте, а разворот знака у серверных чисел;
     точные значения приходят в ответе и повторяются уведомлением — тот же
     приём, что у продажи и заморозки (пробелы 9 и 10);
   - **`mark_effects` у уже отмеченного участника считается от текущего
     остатка**, то есть после списания. `lessons_delta` при этом верен,
     а `lessons_after` врёт на одно занятие: «спишется ещё раз». Интерфейс
     показывает вместо него фактический остаток абонемента — он и есть
     «после отметки». Правильное решение — отдавать в карточке применённый
     эффект отдельным полем (`applied`), а не переиспользовать предпросмотр.
6. **Предпросмотр при нулевом остатке.** Контракт описывает `422` при
   списании с пустого абонемента, но не говорит, как выглядит `mark_effects`
   в этом случае. Мок отдаёт `lessons_delta: -1`, `lessons_after: 0`
   и предупреждающий `summary`; интерфейс подсвечивает такой предпросмотр
   красным, но кнопку не блокирует — решение об отказе принимает сервер.
7. **`branch` в ответе расписания без `timezone`,** в `GET /branches` — с ним.
   Расхождение сохранено в типах как есть; смещение берётся из ISO-строк.
8. **Нет эндпоинта «сегодня» и часового пояса школы.** Дата по умолчанию —
   локальная дата браузера (в мок-режиме — 12 августа 2026, день прототипа).
   Вынесено в `src/lib/today.ts`, чтобы «сегодня» было одно на все экраны.

Этап 2:

9. **Нет предпросмотра продажи.** Контракт требует показать итог до
   подтверждения, но эндпоинта, который его посчитает, не даёт. Итог
   считается на клиенте из полей тарифа (`lessons_count`, `valid_days`,
   `price`) и введённой скидки — это чистая арифметика по данным сервера.
   Промокод в неё не входит: клиент не знает ни списка кодов, ни их действия,
   поэтому промокод помечен как «проверит сервер», а после ответа сумма
   показывается заново из `charged`. Правильное решение —
   `POST /students/{id}/subscriptions/preview` с телом продажи и тем же
   ответом, что у продажи: тогда клиент перестанет считать деньги вовсе.
10. **Нет предпросмотра заморозки.** «Сколько занятий будет отменено»
    известно только серверу — расписания на месяцы вперёд у клиента нет.
    Показываем оценку по темпу абонемента (занятий на день × дней заморозки)
    с пометкой «ориентировочно»; на примере из контракта (11 дней, абонемент
    8 занятий на 31 день) оценка даёт ровно 3 занятия, как в контракте.
    Точное число приходит в ответе и показывается в уведомлении. Нужен
    предпросмотр либо список ближайших занятий ученика в карточке.
11. **`valid_until` при продаже.** Контракт даёт пример: `starts_on`
    1 сентября, `valid_days` 31 → `valid_until` 1 октября. Значит, последний
    день включительно (`starts_on + valid_days − 1`), а не «плюс 31 день».
    Так же считает и мок. Формулу стоит записать в контракт словами.
12. **Фильтр тарифов по направлению не применить.** `GET /plans` принимает
    `discipline_id`, а карточка ученика отдаёт только название направления
    (`"discipline": "Барабаны"`). Тарифы запрашиваются целиком, а тарифы
    направления ученика поднимаются наверх списка на клиенте. Нужен либо
    `discipline_id` в карточке, либо фильтр по имени в `/plans`.
13. **`carry_over_lessons` есть в описании продажи, но нет в `rules`
    карточки.** Ключ объявлен необязательным в типе `SubscriptionRules`;
    когда он приходит, интерфейс показывает строку «Перенос остатка»
    и разрешает галочку переноса, иначе прячет её смысл за подписью
    «правило школы — перенос запрещён». Ключ стоит добавить в пример
    карточки: без него интерфейс не знает, предлагать перенос или нет.
14. **`DELETE .../holds/{hold_id}` описан без тела ответа.** Тип
    `HoldReleaseResponse` объявлен с необязательными полями по аналогии
    с `POST`; интерфейс показывает `valid_until_after` и `lessons_cancelled`,
    если они пришли.
15. **Формат интервала заморозки.** Контракт даёт `from` 14 августа,
    `to` 25 августа и `days: 11` — значит, `to` не входит в интервал
    (полуинтервал, как `daterange` в базе). В диалоге поле подписано
    «По какой (не включая)», чтобы администратор не ошибся на день.
16. **`payer` в поиске и в семье.** Контракт показывает плательщика
    всегда, но у взрослого ученика семьи может не быть. В типах поле
    допускает `null`: строка поиска без телефона полезнее упавшего экрана.
17. **Нет эндпоинта ближайших занятий ученика.** Из-за этого в карточке
    нет блока «следующие занятия», а предупреждение об отменённых занятиях
    при заморозке приблизительное (см. пробел 10).

Этап 3:

18. **Нет справочников преподавателей, кабинетов и направлений.** Клиент
    к ним **готов** (задача #1): `api.teachers(branch_id)`, `api.rooms(branch_id)`,
    `api.disciplines()` описаны в типах и вызываются; моки их отдают.
    Формы справочника нет в контрактах, поэтому типы `DirectoryTeacher`,
    `DirectoryRoom` и `Discipline` собраны по задаче #1 и по схеме базы,
    а всё, чего задача не гарантирует явно, объявлено необязательным.
    Основной источник теперь справочник, запасной — расписание:
    - **диалог пробного** берёт преподавателей и кабинеты из `GET /teachers`
      и `GET /rooms`; если справочник ответил ошибкой или пуст, списки
      по-прежнему собираются из `GET /schedule` (выбранный день плюс
      сегодняшний), но под формой встаёт строка о том, что это срез дня,
      а не справочник, — иначе пропавший преподаватель выглядит как «уволен»;
    - **форма заявки** показывает выбор направления, когда `GET /disciplines`
      ответил. Пустой выпадающий список читался бы как «направлений в школе
      нет», поэтому без справочника поля просто не будет и заявка создастся
      без направления — как и раньше.

    На живом бэкенде все три эндпоинта пока отвечают `404`, и интерфейс
    работает запасным путём. Когда они появятся, менять код не придётся.
19. **`min_age` направления нет в ответе.** Контракт требует сверять
    возраст с минимальным для направления, но `GET /leads/{id}` отдаёт
    только `{id, name}`. Поле объявлено необязательным в типе
    `LeadDiscipline`; мок его присылает, и предупреждение работает.
    Без него интерфейс просто промолчит — жёстко зашивать пороги
    на клиенте нельзя, они у каждой школы свои.
20. **Форма `trial` на доске не описана.** В карточке пробный расписан
    полностью, на доске назван «кратким описанием». Держим одну структуру
    `LeadTrial` с необязательными `status` и `conflicts`: доска
    показывает время, преподавателя и флаг конфликта из тех же полей.
21. **Стадия `trial_booked` вручную.** Контракт разрешает менять стадию
    через `PATCH`, но стадия «пробный назначен» означает занятие
    в расписании. Мок отвечает `422` с указанием нажать «Назначить
    пробный»; если бэкенд решит иначе, интерфейс покажет то, что придёт.
22. **`comment` принимается в `POST /leads`, но не возвращается.** Поле
    объявлено необязательным в `LeadCard` и показывается, когда приходит:
    комментарий «удобно после 18:00» — половина смысла заявки.
23. **`birth_date` при конверсии.** Контракт ждёт дату рождения, а в заявке
    есть только возраст. Поле оставлено пустым и необязательным, рядом
    показан возраст из заявки: выдумывать дату из возраста нельзя —
    она попадёт в базу как факт.
24. **Вебхук `POST /hooks/leads` — не фронтендовый.** Ключи `X-Api-Key`
    интерфейсу не выдаются, экрана управления ключами контракт
    не предусматривает; заявки из внешних источников просто появляются
    на доске с нужным `source`.

## Закрытый долг

- **Отмена ошибочной отметки** (задача #10). Кнопка «Отменить отметку»
  стоит в блоке отмеченного участника, подтверждение показывает, что
  вернётся, после ответа расписание и панель перечитываются. Интерфейс
  рассчитан на состояние **после** исправления уникального индекса
  (задача #2 бэкенда): отменённый участник снова доступен для отметки,
  и мок ведёт себя именно так. Пока индекс не поправлен, живой сервер
  на повторную отметку отвечает `409 mark_revoked` — интерфейс покажет
  его текст в блоке участника и ничего не сломает.
- **Подготовка к справочникам** (задача #1) — см. пробел 18.

## Что не сделано

- Использование отработки (постановка занятия из отработки в расписание):
  контракт этапа 2 отработки только показывает.
- Редактирование заметок и добавление новых: контракт даёт их только
  на чтение.
- Экран «Деньги и ЗП»: вне границ этапа, пункт меню отключён.
- Назначение ответственного за заявку: `PATCH` его принимает, но списка
  пользователей школы контракт не даёт (см. пробел 18) — в карточке
  ответственный только показывается.
- Управление ключами внешних источников и просмотр очереди уведомлений:
  вне границ этапа.
- Автотесты. Этап 3 проверялся на моках: доска и флаги, карточка заявки,
  предупреждение о возрасте, назначение пробного с `422` по кабинету
  и `409` с овербукингом, появление пробного в расписании, перетаскивание
  с откатом при `422`, отказ с причиной, конверсия с переиспользованием
  семьи, дубль заявки по телефону, отчёт по воронке, обе темы.
  Этапы 1–2 проверялись и на моках, и на живом бэкенде
  (`VITE_USE_MOCKS=false`), где карточка Амины, продажа, заморозка
  и снятие заморозки отвечают теми же числами, что в контракте: поиск
  по имени ребёнка,
  по имени и телефону родителя, пустой и короткий запрос, карточка Амины
  и карточка ученика без абонемента, продажа с промокодом и без, продажа
  в долг, отказ по промокоду и по пересечению периодов, заморозка на 11 дней,
  пересечение заморозок (`409`), превышение лимита и дата в прошлом,
  снятие заморозки, переходы из расписания и из панели отметки в карточку,
  обе темы, узкое окно.

  Отмена отметки проверялась на моках (одиночное занятие: отметка → отмена →
  повторная отметка другой отметкой; групповое: две отметки, отмена одной,
  остальные участники не тронуты, занятие остаётся проведённым; день
  с отметками из фикстур; отработка отзывается) и на живом бэкенде
  (`attendance_id` приходит, кнопка появляется, предпросмотр совпал
  с ответом `DELETE`, ошибка сервера показана в блоке участника). Обе темы
  сверены по вычисленным стилям: цвета берутся только из токенов.
