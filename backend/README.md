# Бэкенд RockCRM — этапы 1–5

FastAPI + psycopg 3 + pydantic v2, без ORM. Реализует контракты
[`../docs/contract-v1.md`](../docs/contract-v1.md),
[`../docs/contract-v2.md`](../docs/contract-v2.md),
[`../docs/contract-v3.md`](../docs/contract-v3.md) и
[`../docs/contract-v5.md`](../docs/contract-v5.md):

- **Этап 1.** Справочник филиалов, расписание на день, карточка занятия
  с предпросмотром последствий отметки, применение отметки и её отмена.
- **Этап 2.** Поиск ученика и его карточка (семья, абонемент, журнал
  движений, отработки, заметки, риск оттока), список тарифов, продажа
  и продление абонемента, заморозка и её снятие.
- **Этап 3.** Доска воронки и карточка заявки, заведение вручную и приём
  по вебхуку с ключом, стадии с историей, назначение пробного урока,
  конверсия в ученика, отчёт по воронке.
- **Этап 4.** Ведомость по преподавателям с расшифровкой по занятиям,
  закрытие периода начисления, отчёты владельца: выручка, загрузка
  кабинетов, отток, долги. Контракта у этапа не было — формы описаны
  в пунктах 31–39 ниже.
- **Этап 5.** Вход по телефону с одноразовым кодом (и пароль как альтернатива
  для сотрудников), сессии, роли и права по спецификации §2. Заголовки-заглушки
  `X-Tenant-Id` и `X-User-Id` убраны полностью: школа определяется сессией.
  Контракта у этапа не было — формы описаны в пунктах 40–44 ниже.
- **Кабинет родителя.** Свои дети с остатком и ближайшим занятием, расписание
  всех детей сразу, история с заметками и репертуаром, заявка на перенос
  занятия и на продление абонемента. Контракт —
  [`../docs/contract-v5.md`](../docs/contract-v5.md); очередь заявок для
  администратора контрактом не описана и придумана здесь (пункты 45–50 ниже).
- **Справочники.** Преподаватели, кабинеты и направления отдельными
  ресурсами: формам нужны идентификаторы, а расписание дня справочником
  не является. В контракте их не было — см. пункт 29 ниже.

## Как поднять

Нужен PostgreSQL 17 с расширением `btree_gist` (в официальном образе есть).

```bash
docker run -d --name rockcrm-pg \
  -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=rockcrm \
  -p 55432:5432 postgres:17-alpine

cd backend
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt      # Linux/macOS: .venv/bin/pip
cp .env.example .env                                # при необходимости поправить

.venv/Scripts/python -m scripts.init_db             # создать базу и схему
.venv/Scripts/python -m scripts.seed_demo           # наполнить демо-данными
.venv/Scripts/python -m uvicorn app.main:app --reload --port 8000
```

Документация API — `http://localhost:8000/docs`, проверка живости —
`GET /api/v1/health`.

### Вход

Заголовков `X-Tenant-Id` и `X-User-Id` больше нет. Школа определяется
сессией, сессия выдаётся входом.

```bash
API=http://127.0.0.1:8000/api/v1     # 127.0.0.1, а не localhost: на Windows
                                     # «localhost» уходит в IPv6 и ждёт таймаут

# 1. Запросить код на телефон. Слаг школы обязателен: телефон уникален
#    внутри школы, но не между школами.
curl -s -X POST $API/auth/request-code -H Content-Type:application/json \
  -d '{"tenant":"rockschool-demo","login":"8 701 555 24 18"}'

# Воркера SMS в системе нет — код лежит в очереди уведомлений:
psql "$DATABASE_URL" -c "SELECT payload->>'code' FROM notification
                          WHERE template='auth_code' ORDER BY created_at DESC LIMIT 1"

# 2. Войти. Кука ставится сама (-c), она же уезжает обратно (-b).
curl -s -c cookies.txt -X POST $API/auth/login -H Content-Type:application/json \
  -d '{"tenant":"rockschool-demo","login":"+77015552418","code":"123456"}'

# Сотрудник может войти паролем — в демо это «rockschool»:
curl -s -c cookies.txt -X POST $API/auth/login -H Content-Type:application/json \
  -d '{"tenant":"rockschool-demo","login":"+77015550110","password":"rockschool"}'

curl -s -b cookies.txt $API/auth/me            # кто вошёл и что ему видно
curl -s -b cookies.txt -X POST $API/auth/logout
```

Демо-данные заодно кладут в базу готовые сессии с известным токеном — тем же
приёмом, что и демо-ключи внешних источников: в базе только хеш, открытый
текст известен заранее, потому что это демо. Ими удобно щёлкать curl-ом:

| Токен | Кто | Что проверяет |
|---|---|---|
| `rck_sess_demo_owner` | Ерлан, владелец | видит всё, включая ведомость |
| `rck_sess_demo_admin` | Асель, администратор | без филиалов, без ставок ЗП |
| `rck_sess_demo_branch_admin` | Дана, администратор Абая | чужой филиал не правит |
| `rck_sess_demo_teacher` | Шарапов, барабаны | отмечает только свои занятия |
| `rck_sess_demo_teacher2` | Федько, гитара | второй преподаватель для «чужого» |
| `rck_sess_demo_guardian` | Гульнара Сагындык | видит двоих своих детей |
| `rck_sess_demo_student` | Дмитрий Со, 17 лет | видит только себя |
| `rck_sess_demo_other_owner` | соседняя школа | проверка изоляции |

### Вебхук внешних источников

Тенант определяется ключом, а не заголовками: `X-Tenant-Id` знает любой,
кто открыл фронтенд, и подставить чужую школу было бы тривиально.

```bash
# ключ демо-данных; настоящие выпускаются scripts/make_api_key.py
K=rck_demo_rockschool_leads_key

curl -s -H "X-Api-Key: $K" -H Content-Type:application/json -X POST   -d '{"external_id":"leadhub-8f21c3","name":"Санжар Тлеу","phone":"8 701 555 33 22",
       "student_name":"Санжар","student_age":13,"discipline":"барабаны",
       "source":"telegram_bot","utm":{"utm_source":"instagram"}}'   localhost:8000/api/v1/hooks/leads
# 201 на первую доставку, 200 с той же заявкой на любой ретрай
```

Выпуск и отзыв ключей — административный канал, роли приложения `INSERT`
и `DELETE` на `api_key` не выданы (`db/006_api_keys.sql`):

```bash
.venv/Scripts/python -m scripts.make_api_key <tenant_id> "LeadHub"
.venv/Scripts/python -m scripts.make_api_key --list <tenant_id>
.venv/Scripts/python -m scripts.make_api_key --revoke <key_id>
```

Ключ печатается **один раз**: в базу уходит только SHA-256, восстановить
его нечем. Потерянный ключ не ищут, а выпускают заново.

## Как прогнать тесты

```bash
cd backend
.venv/Scripts/python -m pytest
```

Если в `db/` приехала новая миграция, а база уже поднята, `init_db` её
не увидит — он накатывает схему только на свежесозданную базу. Применить
одну миграцию, не снося данные и не выгоняя чужие соединения:

```bash
.venv/Scripts/python -m scripts.init_db --apply 006_api_keys.sql
```

Тесты пересевают демо-данные **перед каждым тестом**, поэтому направлять их
на базу с нужными данными нельзя — только на `rockcrm_backend`.

**Миграция `010_auth.sql` обязательна.** Без неё нет ни `user_session`,
ни `auth_code`, ни `auth_attempt` — то есть нет входа, а значит не работает
ни один запрос: заголовков-заглушек больше не существует. Пропускать такие
тесты нечего, поэтому проверки «а накатана ли миграция», как у `008` и `009`,
здесь нет: падение на первом же посеве и есть сообщение о том, что стенд
отстал.

```bash
.venv/Scripts/python -m scripts.init_db --apply 010_auth.sql
```

**Миграция `011_family_requests.sql` обязательна так же.** Без таблицы
`family_request` кабинет родителя читается, но заявку подать нечем — то есть
не работает половина этапа. Проверки «а накатана ли миграция» здесь тоже нет
и по той же причине: у `task` нет ни ссылки на занятие, ни желаемого времени,
ни исхода рассмотрения, и обойтись ею нельзя.

```bash
.venv/Scripts/python -m scripts.init_db --apply 011_family_requests.sql
```

Тесты ходят под сессиями, которые кладёт в базу `scripts/seed_demo.py` — тем же
приёмом, что и демо-ключи внешних источников. Служебного пути «войти без
проверки» в приложении не появилось: эти строки ничем не отличаются от выданных
настоящим входом, приложение проверяет их теми же двумя запросами, и живут они
только на базе, которую посеял `seed_demo` (а он начинает с удаления обоих
демо-тенантов). Сам вход — по коду и по паролю, с протуханием, перебором
и выходом — проверяется через настоящий HTTP в `tests/test_auth.py`.

По умолчанию тесты этапов 1–4 ходят **владельцем**: он видит всё, поэтому
они остаются проверками своей предметной области, а не прав доступа.
Разграничение проверяется там, где оно и есть смысл теста, — в `test_authz.py`,
каждой ролью отдельно.

Текущий результат: **411 passed** на базе с миграциями `008`, `009`, `010`
и `011`.
Без них часть тестов пропускается: они сами спрашивают базу, накатана ли
нужная миграция — падать на её отсутствии значит сообщать не о той ошибке.

Даты наступают сами, ни в одном HTTP-запросе, поэтому у системы два ночных
задания — оба надо поставить в cron:

```bash
.venv/Scripts/python -m scripts.sync_statuses            # все школы
.venv/Scripts/python -m scripts.sync_statuses --dry-run  # только показать

.venv/Scripts/python -m scripts.expire_makeups           # сгорание отработок
.venv/Scripts/python -m scripts.expire_makeups --dry-run
```

Оба идемпотентны: второй прогон подряд не меняет ничего, и запуск после
сбоя безопасен.

| Файл | Что закрывает |

## Принятые решения

**Правила отметки — одна функция.** `rules.compute_effect()` вызывают и
предпросмотр в `GET /lessons/{id}`, и применение в `POST .../attendance`.
Второй реализации «для сохранения» не существует. Функция намеренно не зависит
от текущего времени: между предпросмотром и подтверждением проходят минуты,
и любая зависимость от `now()` дала бы редкий невоспроизводимый разъезд между
обещанием и фактом. Сходимость проверяется тестом по всем шести отметкам.

**Правила берутся из `subscription.rules`, а не из `tenant.default_rules`.**
Проданный абонемент — договор на условиях момента покупки. Есть тест: смена
настроек школы не пересчитывает уже проданный абонемент.

**Отдельная база `rockcrm_backend`.** `tests/test_schema.py` пересоздаёт схему
`public` в базе `rockcrm` целиком. Жить с ним в одной базе значит терять данные
ровно тогда, когда кто-то прогонит тесты схемы.

**Одна транзакция на запрос, `set_config` внутри неё.** Единственный способ
получить курсор — пройти через `db.tenant_tx()`, поэтому забыть выставить
тенанта нельзя технически. Используется `set_config('app.tenant_id', %s, true)`,
а не `SET LOCAL`: `SET` не принимает параметры драйвера, а склейка строкой
в самом чувствительном месте системы — прямая дорога к подмене тенанта.
Третий аргумент `true` не даёт значению пережить транзакцию и утечь в следующий
запрос, которому достанется то же соединение из пула.

**SQL руками, без ORM.** Схема уже несёт бизнес-логику: ограничения исключения
против двойной брони, триггер пересчёта остатка, политики изоляции. ORM
пришлось бы учить тем же правилам заново, и они разошлись бы при первой
миграции. В запросах нет `WHERE tenant_id = ...` — его ставит RLS; забытое
условие даёт пустую выборку, а не чужие данные.

**Ошибки базы переводятся по `diag.constraint_name`, а не по тексту.** Текст
зависит от локали сервера. Неизвестное ограничение отдаётся как 500, но с кодом
ограничения в `details` — иначе починить перевод можно только вслепую.

**Остаток блокируется на время транзакции** (`SELECT ... FOR UPDATE` по
абонементу). Без этого два администратора, отмечающие два занятия одного
ученика одновременно, оба увидели бы остаток 1 и оба списали бы.

**Зарплата: нулевое начисление не пишется.** Строка на 0 ₸ — шум в ведомости.
Отмена гасит начисление корректировкой (`kind = 'correction'`), а не удалением:
закрытый период не пересчитывается (spec.md §6.2).

**Остаток не считается в коде нигде.** Продажа пишет `purchase` в журнал
и после этого перечитывает `lessons_balance` из базы, вместо того чтобы
вернуть `plan.lessons_count`. Разница видна только при переносе остатка
(там занятий больше, чем в тарифе), но правило одно: если приложение
складывает дельты само, у остатка появляется второй источник правды,
и однажды они разойдутся.

**Заморозка пишет строку в журнал абонемента.** Обе дельты нулевые —
`entry_nonzero_ck` разрешает такую запись только виду `freeze`. Баланс она
не двигает, но родителю, который спрашивает «почему абонемент кончается
позже» или «куда делось занятие 19 августа», отвечают именно журналом:
аудит он не видит. В `reason` лежит готовая фраза «Заморозка 14–25 августа,
11 дней · каникулы» — её же `ledger` отдаёт заголовком строки. Период
в колонках `subscription_entry` не хранится, и восстановить его из строки
больше неоткуда; обе фразы собирают `rules.freeze_reason()` и
`rules.unfreeze_reason()`, поэтому в базе и на экране написано дословно
одно и то же — журнал читается и без API.

**Снятие заморозки — компенсирующая запись, а не удаление.** Строка
о заморозке остаётся в журнале навсегда (база её и не дала бы тронуть),
а снятие добавляет вторую запись `freeze` с `reverses_id` на исходную.
В истории видно и то, что абонемент замораживали, и то, что заморозку
сняли. Сама строка `subscription_hold` при этом удаляется: это не журнал,
а текущее состояние, и пока она жива, ограничение исключения держит интервал
занятым, а годовой лимит считает эти дни израсходованными — то есть снятая
заморозка продолжала бы действовать.

**Отдельной строки журнала на каждое отменённое занятие нет.** Занятия
не сгорели, они просто не состоятся, а весь период уже описан одной записью
`freeze`. Строка на урок означала бы движение, которого не было. Список
идентификаторов отменённых занятий лежит в аудите.

**Пересечение заморозок проверяется дважды.** Явным запросом — чтобы
сообщение было про пересечение, а не про исчерпанный лимит дней (наложенный
интервал сначала съел бы лимит и вернул бы формально верную, но бесполезную
ошибку). Ограничением исключения в базе — как последняя линия обороны
на случай гонки двух администраторов; оно переводится в тот же `409`.

**Ключ вебхука ищется до того, как известен тенант — и это единственный
запрос без `set_config`.** Политик уровня строк на `api_key` нет намеренно
(`db/006_api_keys.sql`): политика на `current_tenant()` отсекла бы строку
раньше, чем тенант станет известен, и аутентификация внешних источников
стала бы невозможной. Для этого в `db.py` заведён `untenanted_tx()` —
ровно один сценарий, с обязательным `set_tenant()` сразу после проверки
ключа. Пока тенант не выставлен, `current_tenant()` возвращает NULL,
и забывчивость даёт пустую выборку, а не чужие данные.

**Ключ хешируется SHA-256, а не bcrypt.** Медленный хеш защищает пароли,
потому что человек выбирает слабый пароль и его перебирают по словарю.
Здесь секрет — 32 случайных байта, перебирать нечего. Зато ключ проверяется
на каждом запросе вебхука и ищется по индексу; bcrypt не позволил бы ни того,
ни другого — пришлось бы перебирать все ключи школы, которая ещё не известна.

**Идемпотентность вебхука держится на индексе, а не на проверке.** Сначала
читаем по `external_id` (быстрый путь ретрая), но вставка обёрнута в точку
сохранения: два ретрая, пришедшие одновременно, проходят проверку оба,
и второй упирается в `lead_external_uniq`. Без вложенной транзакции эта
ошибка отравила бы всю внешнюю, и прочитать уже вставленную заявку было бы
нечем — а ответить надо именно ею.

**Отчёт по воронке считается когортой по дате создания заявки.** Заявки
берутся по `created_at` в периоде, а переходы — из всей их истории. Если
фильтровать по дате перехода, заявка, пришедшая 30-го и купившая 2-го,
попадёт в знаменатель одного месяца и в числитель другого, и сумма
конверсий не сойдётся ни с чем.

**Стадия `won` не ставится вручную нигде, включая PATCH.** Её пишет только
конверсия, в одной транзакции с созданием ученика. Иначе в отчёте «сколько
стоит пришедший ученик» окажутся те, кто никуда не пришёл.

**Статус `frozen` выводится из фактов, а не хранится снимком.** Схема
объявляла его, триггер берёг, три запроса на него смотрели — и никто его
не ставил: после полугода работы в базе оказалось 64 заморозки и ни одного
`frozen`. Теперь `create_hold` ставит его через `_sync_freeze_status()`,
а снятие возвращает статус, посчитанный по остатку, сроку и наличию
действующей заморозки. Прежний статус нигде не сохраняется намеренно:
за время каникул абонемент мог исчерпаться или истечь, и восстановленный
из снимка `active` разошёлся бы с фактами. Ветки `CASE` повторяют триггер
`subscription_recalc` — иначе первая же запись в журнал переписала бы
статус на свой.

**Заморозка на будущее статус не меняет.** До её начала абонемент
действует: занятия идут, списания идут. Пометить его замороженным заранее
значило бы показать «на каникулах» ученика, который сегодня придёт на урок.
Границу дат — и начало каникул, и их конец — двигает `scripts/sync_statuses.py`:
ни один HTTP-запрос не наступает на дату сам, а без обратного перехода
застрявший `frozen` не дал бы абонементу стать ни `exhausted`, ни `expired`.
Задание идемпотентно и приводит статус к фактам, а не переключает его.

**Срок отработки считается от даты занятия.** «Сгорает через 30 дней»
родитель понимает как 30 дней от пропущенного урока — эта дата есть
в договоре и её можно проверить. От `current_date` срок зависел бы
от расторопности администратора: отметка, внесённая через неделю, давала
бы отработке лишнюю неделю жизни. Дата берётся в поясе филиала.

**Отмена отметки компенсирует ровно то, что удалось отозвать.** Отработку,
потраченную на занятие или сгоревшую по сроку, вернуть нечем: из баланса
она уже ушла. Запись `adjust −1` вычла бы её второй раз и увела баланс
в минус. Сама отработка при этом остаётся в `makeup_credit` — стирать
историю задним числом нельзя. Каскадная отмена занятия, на котором
отработку потратили, в этап не входила: её надо продумывать отдельно.

**Доска воронки отдаётся страницами.** Колонка «Отказ» на живой школе
набирает пятьсот заявок, и целиком её не открывает никто: `GET /leads`
на 688 заявках делал 395 запросов за 1,3 с. Ограничение постадийное
(`?limit=`, по умолчанию 50, потолок 200) — общее съела бы одна большая
колонка. `count` в колонке по-прежнему показывает, сколько заявок в стадии
всего: это счётчик заголовка, и подменять его размером страницы значило бы
врать администратору тем сильнее, чем больше у школы заявок. Сверх
контракта и необязательно добавлены `has_more` и `next_offset`.

**Занятость слотов на доске берётся одним запросом.** `_trial_brief`
спрашивал её на каждую карточку, и это давало почти все 395 запросов.
Теперь `repo.slot_occupants_bulk()` отвечает на всю доску сразу; для одной
заявки остаётся поштучный запрос — собирать пакет ради неё незачем.

**Отработки гасит задание, а не запрос, и ключ идемпотентности — сама
отработка.** У каждой отработки есть `expires_on`, но срок наступает сам
по себе: ни один HTTP-запрос до просроченной отработки не доходит, и без
задания она висит в балансе вечно — школа продолжает быть должна занятие,
право на которое истекло полгода назад. Отметка «задание сегодня отработало»
для идемпотентности не годится: после сбоя на середине пришлось бы выбирать
между «начать заново» (спишет дважды) и «считать день сделанным» (не спишет
вовсе). Ключ — `expired_at` у самой отработки: `UPDATE` берёт только пустые
и возвращает ровно изменённые строки, поэтому в журнал уходит то же
множество, что и в списание. Число сгораний ограничено остатком отработок
абонемента — в согласованных данных это не срабатывает, но задание не имеет
права увести баланс в минус и показать родителю «−1 отработка».

**Сгорание наступает после `expires_on`, а не в этот день.** «Действует
до 1 сентября» родитель понимает как «первого ещё можно», и карточка
показывает такую отработку с `days_left = 0`. В журнале при этом стоит срок
из договора, а не день прогона: задание, опоздавшее на сутки после сбоя,
не должно двигать дату, которую родителю назвали при отмене занятия.

**Годовой лимит заморозки считается по ученику, а не по абонементу.**
Правило `freeze_days_per_year` лежит в абонементе, но лимит в нём годовой,
а абонементов за год несколько. Считать по абонементу значило бы обнулять
лимит каждым продлением, то есть не иметь лимита вовсе.

**Принадлежность начисления периоду хранится колонкой, а не выводится
из даты.** Ведомость закрытого периода читается по `payroll_entry.period_id`,
проставленному при закрытии, а открытого — по датам занятий. Разница между
этими двумя способами и есть всё правило §6.2: отметка, внесённая за июль
после того, как июль закрыт, штампа не получает, в июльскую ведомость
не попадает и уходит в августовскую корректировкой. Если бы период
определялся датой занятия, июльские деньги менялись бы задним числом
после того, как их уже отдали людям на руки, и сверить выплату
стало бы нельзя никогда.

**Открытого периода в системе не существует.** Колонка `closed_at`
в `payroll_period` допускает NULL, но строка заводится сразу закрытой:
пока месяц идёт, начисления просто не проштампованы. Заводить пустой
период заранее значило бы держать состояние, которое ни на что не влияет,
и объяснять администратору разницу между «период не заведён» и «период
заведён, но открыт» — разницы нет.

**Ключ идемпотентности закрытия — `period_id IS NULL`.** Повторное
закрытие не заберёт чужие строки, а сбой на середине не оставит выбора
между «начать заново» и «считать сделанным»: `UPDATE` берёт ровно
непроштампованные. Пересечение периодов ловит ограничение исключения
в схеме, а не проверка в коде.

**Незакончившийся период закрыть нельзя.** Закрытие идущего месяца
отрезало бы от ведомости занятия, которые в нём ещё будут: они появятся
после штампа, штампа не получат и уедут в следующий период — то есть
администратор своими руками создал бы себе полную ведомость корректировок.
Ответ — `422 period_not_over`.

**Выручка — поступившие деньги, а не выставленные счета.** Считается
по `payment`, а не по проданным абонементам. Продажа с долгом — обычное
дело (см. пункт 12), и выручка, показывающая невыплаченное, отвечает
не на тот вопрос: решение «пора ли открывать третий филиал» принимается
по кассе. Возврат лежит в той же таблице отрицательной суммой
и вычитается сам.

**Ёмкость кабинета считается по дням, в которые филиал работал.**
Календаря рабочих дней в схеме нет. Считать рабочими все семь дней недели
значило бы занизить загрузку школы, закрытой по воскресеньям, ровно
на седьмую часть — и ответить «филиал не нужен» там, где он нужен.
Рабочим считается день, в который в филиале было хотя бы одно занятие;
`open_days`, `open_minutes_per_day` и `capacity_minutes` уходят в ответ,
потому что цифру, по которой открывают филиал, надо уметь проверить.

**Ставка в ведомости берётся из самих начислений, а не из `teacher_rate`.**
В ведомости обязана стоять та цифра, по которой посчитали, а не та, что
действует сегодня. Показывается самая частая сумма начисления (`mode`)
и рядом флаг `rate_varies`: у преподавателя ставок несколько — 55 и 85
минут, индивидуальное и группа, — и «4 500 ₸» без оговорки не сходится
с итогом. Неоплаченные отметки в расчёт ставки не идут: отмена заранее —
это не ставка 0.

**Прогулы в ведомости считаются по `attendance.mark`, а не по снимку
`calc`.** `calc` пишет приложение, и у начислений, попавших в базу мимо
него (посев, перенос из старой системы), ключа `mark` в нём нет. Отметка —
факт в своей таблице, и колонка, из-за которой преподаватель спорит
с ведомостью, обязана считаться по факту, а не по полноте снимка.

**Отток считается с отсрочкой.** Ушедшим считается ученик, у которого
абонемент закончился в периоде и не появилось следующего в течение
`grace_days` (по умолчанию 14). Продление покупают и через неделю после
окончания: школа, считающая такого ученика ушедшим, увидела бы отток
в треть и перестала бы верить отчёту вовсе. На ученика берётся один
абонемент — последний закончившийся в периоде, — иначе ученик с двумя
закрывшимися абонементами весил бы в отчёте вдвое больше соседа.

**Сессия — непрозрачный токен в базе, а не JWT.** Подписанный токен нельзя
отозвать, не заведя рядом список отозванных, — то есть ту же таблицу, только
вывернутую наизнанку и с обратной логикой отказа. Уволенный администратор
и потерянный телефон — обычные события в школе, и «выйти на всех
устройствах» обязано срабатывать немедленно, а не «через пятнадцать минут,
когда протухнет access-токен». Второй довод — цена: проверка сессии стоит
один запрос по уникальному индексу, а один запрос на этом фоне не виден
вовсе. В базе лежит SHA-256 от 32 случайных байт, не сам токен: медленный
хеш здесь ничего не добавил бы (перебирать нечего), а стоил бы 60 мс
на каждом обращении к API — то же рассуждение, что и у ключей источников.

**Токен ездит в куке HttpOnly, а `Authorization: Bearer` оставлен вторым
входом.** Фронтенд — отдельное приложение на другом порту, и первым делом
хочется отдать ему токен в ответе и положить в `localStorage`. Так делать
не стали: кабинет родителя — ровно то место, куда однажды прилетит XSS,
а токен в `localStorage` читается любым скриптом на странице и уносится
целиком. Куку `HttpOnly` скрипт не прочитает: он сможет сделать запрос
от имени пользователя, пока страница открыта, но не унести сессию на месяц
вперёд. Разница между «поработал в чужой вкладке» и «получил ключ от
кабинета» стоит того, чтобы платить за неё настройкой CORS.

Тот же токен принимается заголовком `Authorization` — для curl, мобильного
клиента и тестов. Два разных секрета означали бы две таблицы и два способа
их отозвать; браузер при этом заголовком не пользуется и в `localStorage`
ничего не кладёт.

**Кабинет родителя собирается сложением, а не вычитанием.** Ресурсы `/me/*`
не переиспользуют ни `students.card()`, ни его выборки, хотя половина полей
совпадает по именам, — и это стоит одного дублирующего SQL-запроса на каждый
ресурс. Причина в направлении ошибки. Урезание общей карточки ошибается
молча: стоит кому-нибудь добавить поле, и оно уедет родителю, если про него
забыли, а в карточке лежат долг семьи, риск оттока, внутренние заметки
и ставка преподавателя. При сборке сложением ошибка выглядит как
отсутствующее поле — его заметят и попросят, — а не как утечка, о которой
никто не узнает. Проверяется это тоже сложением: тест обходит весь JSON
и падает на любом новом поле, а не сверяет список известных плохих.

**Видимость заметки стоит в условии выборки, а не в фильтре поверх ответа.**
`family_history()` соединяет `lesson_note` с условием `n.visible_to_family`
прямо в `JOIN`, поэтому невидимой заметки в результате не существует вовсе.
Фильтр после выборки («взяли всё, потом убрали») пережил бы ровно до первого
добавления поля, в котором про него забудут, — и внутренняя пометка
преподавателя уехала бы родителю тегом в репертуаре или заголовком строки.

**Состав детей берётся из сессии, а не из параметров запроса.** Все пять
ресурсов кабинета спрашивают `authz.family_student_ids()`, а идентификатор
в пути только сверяется с этим списком. Чужой ребёнок отвечает `404`, а не
`403`, по тому же правилу, что и везде. У сотрудника «мои дети» не
определены вовсе — `visible_student_ids` отвечает владельцу и администратору
«ограничения нет», и кабинет показал бы им всю школу как свою семью; поэтому
роль проверяется отдельно и отвечает `403 family_only`.

**Родитель подаёт заявку, а не двигает расписание.** Слот может быть занят,
преподаватель может быть занят, а перенос одного занятия иногда тянет
за собой второе — решение принимает администратор. `POST` создаёт строку
в `family_request`, задачу в `task` и сообщение в очередь, но ни одного поля
в `lesson` не трогает; это проверяется тестом, который перечитывает занятие
после заявки.

**CSRF закрывает `SameSite=Lax`, а не отдельный токен.** Браузер не приложит
куку к межсайтовому POST, а всё, что меняет данные, у нас POST, PATCH
и DELETE — состояние не меняет ни один GET. Работает это, пока фронтенд
и API на одном сайте: SameSite считается по регистрируемому домену и порт
игнорирует, поэтому `127.0.0.1:5173` и `127.0.0.1:8000` — один сайт, и
`app.school.kz` с `api.school.kz` тоже. Если однажды они разъедутся
по разным доменам, понадобится `SameSite=None; Secure` и вместе с ним
настоящий CSRF-токен — отдельной задачей, а не молчаливой сменой значения
в `.env`.

**Слаг школы обязателен при входе.** Телефон уникален внутри школы
(`person_phone_uniq` по `tenant_id`), но не между школами, и вход «по одному
телефону» означал бы «покажи все школы, где есть этот номер» — то есть выдачу
чужих данных ещё до входа. Фронтенд знает слаг из поддомена, в котором открыт.
Побочный выигрыш: поиск учётной записи идёт уже под выставленным
`app.tenant_id`, то есть под обычной изоляцией строк, и отдельного
привилегированного запроса «найди пользователя во всех школах» в системе нет.

**Ответ на запрос кода одинаков для существующего и несуществующего
телефона — включая маску.** Маска собирается из того, что прислали, а не
из того, что нашлось в базе. Иначе форма входа отвечала бы на вопрос «ходит ли
этот ребёнок в эту школу», и школа раздавала бы персональные данные всем,
кто умеет перебирать номера.

**Код хранится хешем, а доставляется через очередь уведомлений.** Хеш
защищает долговременное хранилище: дамп месячной давности не даёт войти
никуда. Строка в `notification` — это само сообщение, которое через минуту
уедет человеку; воркера, который относит их оператору, в системе пока нет
(см. «Известные ограничения»), и когда он появится, стирать `payload` после
отправки — его работа. Второй канал доставки ради входа заводить незачем:
очередь и есть канал, тот же самый, что у напоминаний об уроке. Тесты читают
код оттуда же, откуда его прочитает человек, — служебной выдачи кода
в ответе API не существует ни под каким флагом.

**Перебор ограничивается тремя разными счётчиками, и каждый закрывает дыру
предыдущего.** Счётчик попыток на самом коде (пять) — иначе миллион вариантов
перебирается за минуты. Лимит на выдачу кодов (три за четверть часа) — иначе
счётчик попыток обходится запросом нового кода. Лимит на неудачные проверки
по логину (десять) — иначе обход работает в обратную сторону. Плюс лимит
по адресу, потому что перебор телефонов школы в лимит на телефон
не упирается никогда.

Счётчики живут в таблице попыток, а не полем в `app_user`: блокировать надо
того, кто ломится, а не учётную запись. Счётчик в учётной записи означал бы,
что посторонний выключает вход владельцу школы, просто перебирая его телефон.

**Отказ во входе возвращается значением, а не исключением.** Исключение
откатило бы транзакцию вместе со счётчиком попыток и строкой в журнале — то
есть лимит перестал бы накапливаться ровно в тех случаях, ради которых он
заведён. Это проверяется отдельным тестом.

**Права разделены на два разных вопроса, и ответы у них разные.** «Можно ли
вызывать операцию вообще» — это роль, и ответ 403. «Какие строки видно
внутри операции» — это фильтр, и ответ 404: разница между «нет такого»
и «есть, но не ваше» сама по себе утечка, по ней перебором пересчитывается
вся школа. Поэтому чужой ребёнок у родителя и чужое занятие у преподавателя
отвечают «не найдено», а продажа абонемента родителю — «нельзя».

**Пустой `staff_branch` означает «без ограничения», а не «никуда нельзя».**
Школа из одного филиала эту связь не заполняет вовсе, и трактовать пустоту
как запрет значило бы выключить вход администраторам у всех, кто её
не трогал. Ограничение действует там, где оно явно задано.

**Ученики преподавателя считаются по трём признакам сразу.** Закреплённые
(`main_teacher_id`), те, у кого он ведёт занятия, и участники групп, которые
он ведёт. Одного признака мало в обе стороны: на замене преподаватель ведёт
чужого ученика и обязан открыть его карточку, а новый закреплённый ученик
ещё ни разу не приходил.

**Ставка преподавателя стала `null`, а не нулём, когда её не видно.** Ноль
читается как «работает бесплатно» и однажды попадёт в разговор. Своя ставка
видна всем, чужая — только владельцу (§2), включая администратора ресепшена:
чужая зарплата — первое, что утекает в чат школы.

**Применённый эффект отметки читается из журнала, а не пересчитывается.**
Предпросмотр и применение — одна функция, и это по-прежнему так. Но
у участника, который уже отмечен, вопрос другой: не «что будет», а «что
случилось». Пересчёт правилами вернул бы не то, что списывалось: правила
школы могли смениться, а проданный абонемент живёт по правилам момента
покупки. `applied_effect` собирается из `subscription_entry`
и `payroll_entry` по `attendance_id`.

## Где контракт оказался неполным и что сделано

1. **`cancelled_late` не описан ни в spec.md, ни в контракте.** Из шести
   отметок таблица §4.3 покрывает пять. Поздняя отмена привязана к тому же
   правилу, что и прогул (`no_show_burns`, `pay_teacher_on_no_show`): по смыслу
   это тот же несостоявшийся урок, и школа, отключившая сгорание прогула,
   вряд ли имела в виду обратное.

2. **Противоречие про отмену преподавателем.** Таблица spec.md §4.3 и §5.3
   говорят «+1 отработка», а `tenant.default_rules.teacher_cancel_effect`
   в схеме — `no_charge`, и прототип показывает то же. Реализовано по правилу
   из абонемента: `makeup` даёт отработку, `no_charge` — нет. По умолчанию
   отработки не будет. **Нужно решение владельца продукта.**

3. **`mark_effects` не имел поля «почему нельзя».** Добавлены два поля сверх
   контракта: `blocked_reason` (текст, если отметку применить нельзя — например,
   нулевой остаток) и `makeups_after` (симметрично `lessons_after`). Оба
   аддитивны и старый фронтенд не ломают. Без `blocked_reason` интерфейс мог бы
   только показать 422 после нажатия, что противоречит идее предпросмотра.

4. **`attendance_id` не отдавался в карточке занятия.** Без него вызвать
   `DELETE /attendance/{id}` не из чего. Добавлен в `participants[]`.

5. **Ответ `DELETE /attendance/{id}` в контракте не описан** — сказано только
   «200 с описанием компенсации». Возвращается
   `{attendance_id, mark, revoked_at, reverted: {...}, lesson_status}`, где
   `reverted` повторяет форму `applied` из `POST`.

6. **`attendance_mark` в расписании — одно значение на занятие**, а отметки
   хранятся по ученику. Для группы, где один пришёл, а другой прогулял, одного
   значения не существует: возвращается `null`, детали видны в карточке.

7. **Пробный урок по заявке отметить нельзя.** `attendance.student_id` обязателен,
   а у лида ученика ещё нет. Такое занятие отдаётся с `participants: []`
   и заголовком из заявки; `POST` отвечает `422 lead_lesson`. Это ограничение
   схемы, а не недосмотр: отмечать посещаемость нужно после конверсии заявки.

8. **`status = held` ставится после первой отметки при любой отметке**, как
   требует контракт, — включая `cancelled_teacher`. Выглядит спорно: занятие,
   отменённое преподавателем, помечено как проведённое. Менять контракт
   в одностороннем порядке не стал. При отмене последней отметки статус
   возвращается в `planned`.

9. **`room_utilization_pct` считается честно**: занятые минуты кабинетов
   делятся на «число кабинетов филиала × часы работы». В контракте стоит `74`,
   на демо-дне выходит `36` — пример в контракте был декоративным.

### Этап 2

10. **Границы интервала заморозки контракт не определяет.** По примеру
    «с 14 по 25 = 11 дней» интервал полуоткрытый, `[from, to)` — ровно так
    его и хранит `daterange` в схеме. Значит, 25-е число в заморозку
    **не входит** и занятие 25-го не отменяется. Иначе дней было бы 12,
    и пример контракта перестал бы сходиться сам с собой.

11. **«Школа это запрещает» про пересечение абонементов — правила
    не существовало.** Реализовано как «запрещено по умолчанию»: продажа
    второго абонемента на тот же период даёт `422 subscription_overlap`
    с подсказкой, с какой даты продлевать. Разрешается ключом
    `allow_overlapping_subscriptions: true`. Блокируются только абонементы
    **с непотраченным остатком**: исчерпанный абонемент текущего месяца —
    обычная причина продать новый прямо сейчас. **Закрыто:** ключ добавлен
    в `tenant.default_rules` со значением `false`.

12. **`debt` в контракте не определён формулой.** Считается как «начислено
    по абонементам семьи минус поступившие платежи, но не меньше нуля».
    Начисленное выводится из `price` и `discount_pct`, зафиксированных
    в самом абонементе: отдельного поля «сумма к оплате» в схеме нет.
    В ответе продажи `debt` — долг по этой продаже, в карточке — долг семьи.

13. **`family` может быть `null`.** У ученика без семьи (`student.family_id
    IS NULL`) семьи не существует, и выдумывать её из самого ученика значило
    бы показывать в интерфейсе несуществующего плательщика. Фронтенду
    придётся обработать `null` — так же, как у `subscription`.

14. **`ledger` отдаётся по всем абонементам ученика, а не только по текущему.**
    Контракт кладёт его рядом с `subscription`, но вопрос «куда делось
    занятие» не обрывается на дате продления. Ограничен сотней последних
    записей.

15. **`amount` в журнале заполняется только у покупки** — суммой реально
    поступивших платежей по этому абонементу. У Амины это 48 600 ₸
    (54 000 ₸ со скидкой 10%), а не 54 000 ₸, как нарисовано в прототипе:
    прототип показывал цену тарифа, а журнал показывает деньги.

16. **Формулу `churn_risk` контракт оставил на усмотрение.** Веса
    в `rules.churn_risk()`: прогул за 30 дней +30 (до 60), остаток ≤ 2 +25,
    нет абонемента +45, срок истекает в течение недели +12, нет занятий
    2 недели +15 (4 недели +30); стаж от полугода и от трёх купленных
    абонементов снимают по 8. Уровни: `medium` от 20, `high` от 55.
    Каждая причина — счётный факт.

    **`reasons` содержит только то, что риск повышает.** Стаж и число
    купленных абонементов — доводы против оттока, и в списке причин риска
    «занимается 6 месяцев» читалось бы как довод за. Они снижают счёт
    и уходят отдельным полем `mitigations` (сверх контракта) — тем же
    проверяемым фактом, но на своей стороне весов. Интерфейс волен показать
    их рядом, как в прототипе.

17. **Ответы продажи и заморозки дополнены полями.** `carry_over_note` —
    почему перенос не состоялся (контракт требует показать это явно,
    а голый `carried_over: 0` ничего не объясняет). `message` у заморозки
    и её снятия — та же информация одной фразой для тоста. `lessons_restored`
    у снятия — всегда `0`, и это явное обещание, а не умолчание.
    `churn_risk.mitigations` — факты, снизившие оценку. В строке журнала
    добавлено поле `reason` — исходная причина, как её сохранил журнал:
    заголовок годится для экрана, а в спорном случае нужен и первоисточник.

18. **Групповые занятия заморозка не отменяет.** Отменяются занятия, где
    ученик стоит как `lesson.student_id`. Отменить занятие группы из-за
    каникул одного участника нельзя, а отметить его отсутствие постфактум
    можно обычной отметкой.

### Этап 3

19. **Цене пробного урока в схеме места нет.** Контракт присылает
    `price: 2000`, а у `lesson` нет колонки цены. Записывать `payment`
    было бы враньём: способ оплаты в запросе не приходит, а платёж без
    метода — это деньги, которых никто не получал. Цена принимается,
    уходит в аудит операции и возвращается в ответе. **Нужна либо колонка
    `lesson.price`, либо `payment.method` в запросе.**

20. **Комментарий администратора складывается в `utm`.** Отдельной колонки
    под «хочет вечером после 19» в `lead` нет, а это ровно то, ради чего
    перезванивают. Лежит как `utm.comment`; поле `utm` — jsonb, схема
    не нарушена, но по имени поля этого не видно.

21. **Ответ `PATCH /leads/{id}` контракт не описывает.** Возвращается
    карточка целиком — та же, что у `GET`: интерфейсу после смены стадии
    всё равно нужно перерисовать карточку, и второй запрос за ней был бы
    лишним кругом.

22. **`GET /leads?stage=` возвращает одну колонку, а не шесть.** Пустая
    колонка на доске означает «здесь ничего нет», а не «сюда не смотрели»,
    и отдавать пять пустых в ответ на фильтр было бы обманом.

23. **`waiting_for` считается от последней смены стадии, а не от создания.**
    Контракт говорит «с момента последней смены стадии», и это единственное
    осмысленное чтение: время с создания показывало бы «неделя» у заявки,
    по которой вчера провели пробный.

24. **`conversion_trial_to_won_pct` в сводке доски** — доля тех, кто побывал
    в `trial_held`, среди них же дошедших до `won`, за последний год. Год,
    а не месяц: конверсия по трём заявкам за неделю не значит ничего.
    Заявка, купившая сразу из `trial_booked`, минуя `trial_held`,
    в знаменатель не попадёт.

25. **Первая строка истории пишется с `from_stage = NULL`.** Контракт
    говорит только про «смену стадии», но без записи о входе в `new`
    у стадии нет момента входа, и отчёт не может посчитать ни её конверсию,
    ни время, которое заявка провисела нетронутой.

26. **Проверка дубля по телефону смотрит только незакрытые стадии.** Тот же
    человек через полгода со вторым ребёнком — это новая заявка, а не дубль,
    и блокировать её значило бы прятать реальный спрос из воронки.

27. **`assigned_to` в карточке — объект `{id, name}`, а в `PATCH` — строка
    с UUID.** Так в контракте, и это осознанная асимметрия: читателю нужно
    имя, писателю — идентификатор.

28. **Заявка не проверяет, что филиал и кабинет из одной школы явно.**
    Это делает RLS: кабинет чужой школы просто не найдётся, и ответ будет
    `404`, а не «нельзя». Отдельной проверки нет намеренно — она дублировала
    бы изоляцию и однажды разошлась бы с ней.

29. **Справочников в контракте не было вовсе.** Формам нужны `teacher_id`,
    `room_id` и `discipline_id`, а взять их было неоткуда: интерфейс
    выковыривал преподавателей и кабинеты из `GET /schedule`, то есть
    из тех, у кого в выбранный день есть занятия. Это работало случайно —
    расписание отдаёт срез дня, и преподаватель с выходным в диалог
    не попадал, — а направление в форме заявки выбрать было нельзя вовсе,
    и заявка уходила в воронку без него, мимо отчёта по направлениям.
    Добавлены `GET /teachers`, `GET /rooms`, `GET /disciplines` — чистый
    слой чтения, всё уже лежит в схеме. Фильтры `?branch_id=`
    и `?discipline_id=` сверх контракта: «кто ведёт барабаны в Аль-Фараби» —
    это вопрос формы, и отвечать на него выборкой всего списка на клиенте
    незачем. Направления и филиалы отдаются объектами `{id, name}`, а не
    названиями: по названию нельзя ни отфильтровать, ни подставить
    идентификатор в запрос.

30. **`min_age` не приходил вместе с направлением.** Контракт требует
    предупредить, если ребёнок младше минимального возраста («барабаны
    с 5, скрипка с 7»), но карточка заявки отдавала направление как
    `{id, name}`, и интерфейс объявил проверку необязательной. Готовая
    фраза `age_warning` (сверх контракта) была, а числа не было — а оно
    нужно, чтобы подсветить поле возраста и сравнить его при вводе,
    не дожидаясь ответа сервера. Порог зашить в клиент нельзя: это
    настройка школы, и первая же школа, берущая на барабаны с четырёх,
    сломала бы захардкоженную таблицу. Теперь `min_age` едет в объекте
    направления и в `GET /disciplines`; предупреждение и порог считаются
    из одного поля и разъехаться не могут.

### Этап 4

31. **Контракта у этапа не было вовсе.** Формы придуманы здесь и держатся
    стиля этапов 1–3: плоские предсказуемые объекты, деньги целым числом
    тенге, даты ISO. Период везде задаётся парой `from`/`to`
    **включительно** — «по 31 июля» человек читает как «июль целиком»,
    и полуоткрытый интервал в API заставил бы интерфейс каждый раз
    прибавлять день. Внутри и в схеме (`daterange '[)'`) граница
    исключительна; преобразование живёт в одном месте — `money.py`.
    Без `from`/`to` берётся текущий месяц в поясе школы.

32. **Ведомость и её расшифровка — два ресурса, а не один.**
    `GET /payroll` отдаёт строку на преподавателя, `GET /payroll/teachers/{id}` —
    строку на начисление. Складывать их в один ответ значило бы тянуть
    на экран все начисления школы за месяц ради таблицы из пяти строк:
    на симуляции это 682 записи против 10.

33. **Закрытие периода — одна операция, а не «создать, потом закрыть».**
    `POST /payroll/periods` c `{from, to}` заводит период и сразу закрывает
    его. Причина в пункте «Открытого периода в системе не существует» выше.
    Ответ — сводка закрытия (`entries`, `teachers`, `total`) и готовая
    фраза `message` для тоста.

34. **`carried_over` — сверх любого разумного минимума, и без него нельзя.**
    В открытой ведомости лежат правки за уже закрытые месяцы, и сумма
    перестаёт делиться на число занятий. Число и сумма таких строк едут
    отдельными полями в каждой строке ведомости и в итогах, а в расшифровке
    строка помечена флагом `carried_over`. Иначе преподаватель видит в своей
    ведомости дату из прошлого месяца и считает, что ему приписали лишнее.

35. **Выручка отдаётся всеми тремя разрезами сразу**, а не по `?group_by=`.
    Экран показывает их одновременно, и три запроса вместо одного дали бы
    три разных момента времени в одной шапке. Разрезов на самом деле четыре:
    к филиалам, направлениям и месяцам добавлен способ оплаты — «сколько
    из кассы прошло мимо Kaspi» это тот же вопрос про деньги.

36. **Платёж без абонемента попадает в строку «Не распределено».**
    У него нет ни филиала, ни направления: и то и другое выводится через
    `subscription → student` и `subscription → plan`. Прятать такие деньги
    нельзя — сумма разрезов перестала бы сходиться с итогом.

37. **Отток отдаёт и проценты, и поимённый список.** «7% за август» без
    имён — это цифра, с которой нечего делать. `students[]` ограничен
    `?limit=` (по умолчанию 50), `by_teacher[]` отсортирован по числу
    ушедших: первым идёт тот, к кому идти разбираться.

38. **У долгов периода нет.** Долг — это состояние на сейчас, а не событие
    в интервале, и `?from=&to=` у него означал бы что-то третье. Формула
    та же, что в карточке семьи (пункт 12), и это проверяется тестом:
    отчёт и карточка обязаны называть родителю одну сумму.

39. **`applied_effect` в карточке занятия — сверх контракта этапа 1.**
    Появился по issue #22: интерфейс, показывая блок «Отмечено», брал числа
    из `mark_effects`, то есть из предпросмотра, посчитанного от уже
    уменьшенного остатка — дельта совпадала, а `lessons_after` отставал
    ровно на списанное занятие. Теперь у отмеченного участника два разных
    поля на два разных вопроса: `applied_effect` — факт из журнала,
    `mark_effects` — по-прежнему предпросмотр «что будет, если
    переотметить», но считается от остатка **до** списания (переотметка
    начинается с отмены прежней отметки, и она вернёт занятие назад).
    Оба поля аддитивны. **Обход на клиенте
    (`AttendancePanel.tsx`, подстановка `subscription.lessons_balance`
    вместо `lessons_after`) теперь лишний и должен быть снят.**

### Этап 5

40. **Контракта у этапа не было.** Формы держатся стиля этапов 1–4.
    Четыре ресурса: `POST /auth/request-code`, `POST /auth/login`,
    `POST /auth/logout`, `GET /auth/me`. Ошибки — те же
    `{"error": {code, message, details}}`, что и везде.

41. **`GET /auth/me` — сверх любого минимума, и без него нельзя.**
    Интерфейс рисует разные экраны разным ролям, а роль, вычисленная
    на клиенте, — это роль, которую клиент себе назначил. Вместе с ролью
    едут `branch_ids` (что показывать в переключателе филиалов)
    и `student_ids` (кабинету родителя — сразу, без второго запроса).

42. **`POST /auth/logout` отвечает 200 с телом, а не 204.** Пустой ответ
    нечем отличить от «прокси съел запрос», а тост «Вы вышли из всех
    сеансов» отличается от «Вы вышли» — и это разные действия.

43. **Ответ входа содержит `token`, хотя фронтенду он не нужен.** Кука
    выставляется тем же ответом, и браузеру достаточно её. Поле оставлено
    для curl, мобильного клиента и тестов; класть его в `localStorage`
    фронтенду не надо — весь смысл `HttpOnly` в том, что там его нет.

44. **`teacher.rate` в карточке занятия сменил тип на `int | null`.**
    Аддитивно по смыслу, но не по типу: интерфейс, показывающий ставку
    администратору, обязан обработать `null` — это «вам не видно»,
    а не «ставки нет».

### Кабинет родителя

45. **Очередь заявок в контракте не описана вовсе.** Контракт заканчивается
    на «заявка создаёт задачу администратору», но экрана, на котором её видно
    и на котором на неё отвечают, в нём нет — то есть кабинет обещал бы
    родителю ответ, а выполнить обещание было бы нечем. Добавлены
    `GET /requests` и `PATCH /requests/{id}` (админ и владелец). Формы держатся
    стиля этапов 1–4.

    `GET /requests?status=&kind=&limit=` — `status` по умолчанию `pending`
    (плюс `accepted`, `declined`, `all`), `kind` — `reschedule` или `renew`.
    Ответ: `{counts: {pending, reschedule, renew}, requests: [{request_id,
    kind, status, created_at, student: {student_id, name}, requested_by:
    {name, phone}, lesson: {lesson_id, starts_at, status, teacher, branch,
    room} | null, reason, preferred[], answer, answered_by, answered_at,
    moved_to}]}`. Нерассмотренные идут первыми и **старыми сверху**: заявка,
    которую не заметили три дня, важнее пришедшей минуту назад. `counts`
    считается по всей школе, а не по странице, — это счётчик заголовка.

    `PATCH /requests/{id}` принимает `{status: accepted|declined, answer,
    moved_to}` и возвращает ту же заявку плюс готовую фразу `message`.
    Ошибки: `404` — чужая или несуществующая; `409 already_answered` —
    заявка уже рассмотрена; `422 answer_required` — отказ без объяснения;
    `422 moved_to_not_applicable` — занятие указано у заявки на продление.

46. **`PATCH /requests/{id}` НЕ переносит занятие.** Редактирования расписания
    в системе нет вовсе (см. «Известные ограничения»), и делать вид, что
    согласие заявки двигает урок, значило бы врать обеим сторонам сразу.
    Администратор двигает занятие тем же способом, что и раньше, а `moved_to`
    проставляет, чтобы в заявке было видно, чем всё кончилось.

47. **Повторная заявка отвергается, и у переноса это делает база.**
    Частичный уникальный индекс `family_request_one_open` не даёт двум
    открытым заявкам жить на одном занятии; приложение проверяет то же самое
    заранее, чтобы ответить `409 request_exists` внятной фразой, а не кодом
    ограничения. У продления такого индекса нет (заявка не привязана
    к занятию) — там проверка только в коде, и это осознанная разница:
    двойное нажатие она ловит, гонку двух вкладок — нет, и цена гонки здесь
    вторая строка в очереди администратора, а не двойное списание.

48. **`reschedule_request` в расписании — сверх контракта.** Контракт даёт
    `can_request_reschedule`, но не даёт способа узнать, что заявка уже
    подана. Без этого кабинет предложил бы подать её второй раз и получил бы
    `409` там, где всё в порядке. Поле аддитивно: `null` или
    `{request_id, status}`. Сам флаг `can_request_reschedule` при этом
    считается ровно по контракту (порог отмены и «занятие ещё не проведено»)
    и той же функцией, что отвечает на `POST`, — иначе интерфейс показывал бы
    кнопку, а сервер отказывал, и это выглядело бы как поломка.

49. **`history` дополнена `title` и `makeups_delta`.** Контракт показывает
    строку истории с датой, отметкой и дельтой занятий, но у покупки отметки
    нет вовсе, а у отмены заранее двигается не остаток, а отработки —
    родитель увидел бы «+8» и «0» без единого слова о том, что произошло.
    `title` — та же человеческая формулировка, что и в журнале администратора
    (`rules.ledger_title`), и это единственное, что кабинет переиспользует:
    фразы обязаны совпадать дословно, иначе спор с родителем разбирают
    по двум разным текстам.

50. **`teacher` в `/me/children` — объект, а в карточке ребёнка строка.**
    Так в контракте, и менять не стал: в списке `{"name": …}` оставляет место
    для фотографии преподавателя, ради которой объект и заведён. Ставки нет
    ни там, ни там, и поля под неё не существует.

## Известные ограничения

**Переотметка занятия требует миграции `008`.** Приложение больше не знает
про отменённые отметки: действующей считается строка с пустым `revoked_at`,
и ровно это держит частичный индекс `attendance_active_uniq`. Пока миграция
не накатана, в базе живёт сплошной `UNIQUE (lesson_id, student_id)`, и
переотметка после отмены упирается в него — ответ будет тот же `409
already_marked` (имя старого ограничения оставлено в `errors.py` именно
затем, чтобы отставший стенд не отдавал 500). Тест переотметки в
`test_attendance_api.py` спрашивает базу и пропускается, если индекса нет.

**Кода никто не отправляет.** Одноразовый код ложится в `notification`
и остаётся там: воркера очереди в системе нет вовсе (см. ниже про
уведомления). До его появления вход по коду работает только там, где очередь
кто-то читает руками, — то есть в разработке и в тестах. Это единственное,
что отделяет вход от боевой готовности, и чинится оно вместе с отправкой
всех остальных уведомлений.

**Сессии не показываются человеку и не чистятся.** «Мои устройства» с датой
последнего входа собирается из `user_session` одним запросом, но экрана нет —
есть только `POST /auth/logout?everywhere=true` вслепую. Протухшие строки
никто не удаляет: они безвредны (`expires_at` проверяется запросом), но
таблица растёт, и уборку придётся поставить в cron рядом с двумя ночными
заданиями.

**Смены пароля и его выдачи в приложении нет.** `password_hash`
проставляется посевом; настоящий сотрудник получает пароль тем же
административным каналом, что и ключи внешних источников. Вход по коду
работает и без пароля, поэтому дырой в сценарии это не является, но
«сменить пароль» на экране профиля однажды спросят.

**Второго фактора нет.** Владелец школы видит всю кассу и все зарплаты,
и одного SMS-кода для такой роли мало. Задача отдельная: она тянет за собой
и коды восстановления, и экран управления устройствами.

**Ответ на заявку доходит до родителя только очередью уведомлений.**
Кабинет обещает «ответ придёт сообщением», и сообщение действительно
встаёт в `notification` — но воркера, который относит его в WhatsApp,
в системе по-прежнему нет (см. ниже). Своего экрана «мои заявки»
у родителя тоже нет: рассмотренная заявка исчезает из расписания вместе
с `reschedule_request`, и текст ответа он увидит там, где увидит все
остальные сообщения школы. Список заявок родителя — отдельный ресурс,
и заводить его до появления воркера незачем: он показывал бы ответ,
который родителю уже отправили.

**Перенос по принятой заявке администратор делает руками.** Операции
«подвинуть занятие» в приложении нет вовсе, поэтому `PATCH /requests/{id}`
меняет только саму заявку. Пока расписание не редактируется через API,
иначе и быть не может; когда появится — согласие заявки должно двигать
занятие одной транзакцией и проставлять `moved_to` само.

**Заявка на продление ничего не продаёт.** Она заводит задачу
администратору, и оплата идёт через ресепшен: приём платежей через
провайдера — отдельная интеграция, а обещать оплату, которой нет, хуже,
чем её отсутствие. Телефон и WhatsApp школы рядом с кнопкой — обязанность
интерфейса, а не бэкенда.

**Ставка процентом считается от стоимости занятия абонемента** (`price /
lessons_total`). Другой цены урока в схеме нет; для занятия без абонемента базы
для процента не существует и начисляется 0. В демо-данных все ставки
фиксированные.

**`paid_this_month` привязан к календарному месяцу сервера.** Считается
по `date_trunc('month', now())`, то есть в поясе базы, а не филиала. Разница
проявится только у школы с филиалами в разных часовых поясах и только
в первые часы месяца; чинится вместе с переходом всей отчётности на пояс
филиала.

**Заморозка на стыке годов расходуется из года начала.** Интервал
с 25 декабря по 8 января целиком списывается с лимита декабрьского года.
Дробить его между годами схема позволяет (`period * daterange(год)` уже так
и считает использованное), но проверка при создании смотрит на один год —
поведение на стыке нужно согласовать с владельцем продукта.

**Отмена продажи не реализована.** Ошибочно проданный абонемент гасится
вручную: записи журнала неизменяемы, а компенсирующей операции
(`subscription.cancel` с возвратом платежа) в контракте этапа нет.

**Уведомления только встают в очередь.** Воркера, который относит их
в WhatsApp, нет — и это по границам этапа. Строка `notification` ложится
на диск в одной транзакции с занятием: если транзакция откатится,
напоминание о несуществующем пробном не уйдёт.

**Пробный не переносится и не отменяется отдельной операцией.** Повторное
`POST /leads/{id}/trial` создаёт второе занятие, а не двигает первое;
на доске и в карточке показывается последнее назначенное. Напоминание
при этом не задваивается — у каждого занятия свой `dedup_key`, — но
у отменённого пробного напоминание остаётся в очереди. Перенос пробного
в контракт этапа не входил.

**Отдельного эндпоинта `api_key` нет.** Выпуск и отзыв идут скриптом под
административной ролью: приложению `INSERT` и `DELETE` на `api_key`
не выданы схемой, и обходить это через API значило бы спорить с решением,
записанным в `db/006_api_keys.sql`.

**Заморозка на стыке дня всё ещё зависит от того, кто спрашивает.**
`sync_statuses` берёт «сегодня» в поясе школы, а `expired` считается
по `current_date` сервера — так же, как в триггере. У школы с филиалами
в разных поясах эти два дня разойдутся на несколько часов; чинится вместе
с переходом всей отчётности на пояс филиала.

**Отработка сгорает по своему сроку, но не по окончании абонемента.**
`expire_makeups` гасит просроченные, а отработка, выданная за неделю
до конца абонемента, доживает свои тридцать дней и после того, как
абонемент истёк. Правило «остаток и отработки сгорают вместе со сроком»
в спецификации не сформулировано, а угадывать его — значит списывать
у родителя то, о чём с ним не договаривались. **Нужно решение владельца
продукта.**

**Закрытый период нельзя открыть обратно.** Обратной операции нет
намеренно: «переоткрыть июль» означает «пересчитать выплаченное», а это
ровно то, что §6.2 запрещает. Ошибка в закрытии чинится через базу
административным каналом — как и всякая правка журнала.

**Бонусы и удержания начислять нечем.** `payroll_entry.kind` знает
`bonus` и `deduction`, ведомость их показывает отдельными колонками,
но операции, которая их создаёт, в приложении нет: в этап входило
чтение и закрытие, а «премия преподавателю» — отдельный разговор
про права (её ставит владелец, а не администратор ресепшена).

**Ведомость не знает, выплачены ли деньги.** `payroll_period` фиксирует,
что период посчитан и закрыт, но факта выплаты в схеме нет — ни суммы,
ни даты, ни способа. Отличить «посчитали» от «отдали» сейчас нельзя.

**Отток считается по абонементам, а не по архивации ученика.**
`student.churn_reason` и `archived_at` в схеме есть, но их никто
не заполняет: операции «ученик ушёл» в приложении нет. Отчёт поэтому
опирается на факт «абонемент кончился и не продлён» — он наблюдаем
и проверяем, но причину ухода не знает.

**Выручка по филиалу берётся из филиала ученика, а не занятия.** Ученик,
ходящий в два филиала, целиком записывается в тот, что стоит
в `student.branch_id`. Разнести платёж по филиалам фактически посещённых
занятий схема позволяет, но это уже распределение выручки, а не факт
платежа, и правило распределения нужно согласовать со школой.

**Не реализовано и не входило в этап:** редактирование расписания,
сгорание остатка занятий по окончании срока абонемента, проведение занятия
по отработке, отправка уведомлений (воркер очереди),
приём платежей через провайдера, выплата зарплаты (в отличие от её
начисления и закрытия периода), сквозная аналитика расходов на рекламу.
