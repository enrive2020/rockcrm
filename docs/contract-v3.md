# Контракт этапа 3 — «Воронка заявок»

Продолжение [этапа 1](contract-v1.md) и [этапа 2](contract-v2.md).
Транспорт, аутентификация, формат ошибок и часовой пояс — оттуда.

---

## Зачем этот этап

Заявки в школу приходят из Telegram-бота, формы сайта, WhatsApp и Instagram,
и теряются между ними: администратор помнит, кому перезвонить, до конца
смены. Отсюда же берётся единственный вопрос, на который школа сейчас
не может ответить цифрами — **сколько стоит один пришедший ученик**
и какой источник его привёл.

Этап замыкает путь: заявка → дозвон → пробный урок → покупка абонемента,
и подключает существующие проекты `LeadHub` и `Telegram-Bot` как источники.

## Границы этапа

Входит:

- Доска воронки по стадиям, карточка заявки
- Заведение заявки вручную и приём по вебхуку от внешних источников
- Перевод по стадиям с историей, назначение ответственного, напоминание
  «перезвонить»
- Назначение пробного урока — с занятием в расписании
- Конверсия заявки в ученика с абонементом
- Отчёт по воронке: конверсия между стадиями и по источникам

Не входит: кабинет родителя, уведомления в WhatsApp (только постановка
в очередь `notification`), сквозная аналитика расходов на рекламу.

## Что уже есть в схеме

`lead`, `lead_stage_history`, `notification`, `task`, `api_key`.
Менять схему нельзя. Стадии и причины отказа заданы ограничениями
в `db/004_sales.sql` — используйте их значения дословно.

Пробный урок — это обычная запись в `lesson` с заполненным `lead_id`
вместо `student_id`; расписание этапа 1 уже умеет её показывать.

## Ресурсы

### `GET /api/v1/leads?stage=&source=&assigned_to=&branch_id=`

Доска. Визуальный ориентир — экран «Заявки» в `prototype/index.html`.

```json
{
  "columns": [
    {
      "stage": "new", "title": "Новая", "count": 3,
      "leads": [
        {
          "id": "...", "name": "Алиса Ким",
          "student_name": "Алиса", "student_age": 7,
          "discipline": "Барабаны", "source": "telegram_bot",
          "phone": "+77015551234",
          "created_at": "2026-08-11T14:20:00+05:00",
          "waiting_for": "2 часа",
          "next_action_at": null,
          "contact_attempts": 0,
          "assigned_to": {"id": "...", "name": "Айгерим Дюсенова"},
          "trial": null,
          "flags": ["no_answer"]
        }
      ]
    }
  ],
  "summary": {
    "total": 12, "overdue": 2,
    "conversion_trial_to_won_pct": 61,
    "avg_days_to_won": 4
  }
}
```

- Стадии и их порядок: `new` → `contacting` → `trial_booked` →
  `trial_held` → `won`, плюс `lost` отдельной колонкой.
- `waiting_for` — человеческая длительность с момента последней смены
  стадии: «2 часа», «3 дня». Именно она показывает застрявшие заявки.
- `flags` — то, на что администратор обязан среагировать:
  `no_answer` (две и более неудачных попытки), `overdue`
  (`next_action_at` в прошлом), `trial_today`, `trial_conflict`
  (пробный стоит в занятом кабинете).
- `trial` — краткое описание назначенного пробного или `null`.

### `GET /api/v1/leads/{id}`

```json
{
  "id": "...", "name": "Алиса Ким", "phone": "+77015551234",
  "student_name": "Алиса", "student_age": 7,
  "discipline": {"id": "...", "name": "Барабаны"},
  "branch": {"id": "...", "name": "Аль-Фараби 53В"},
  "stage": "trial_booked", "lost_reason": null,
  "source": "telegram_bot", "utm": {}, "promo_code": null,
  "assigned_to": {"id": "...", "name": "Айгерим Дюсенова"},
  "next_action_at": "2026-08-12T18:00:00+05:00",
  "contact_attempts": 1,
  "created_at": "2026-08-11T14:20:00+05:00",

  "trial": {"lesson_id": "...", "starts_at": "2026-08-12T13:00:00+05:00",
            "teacher": "Егор Мадратов", "room": "Барабанная A",
            "status": "planned", "conflicts": []},

  "history": [
    {"at": "2026-08-11T16:05:00+05:00", "from": "new", "to": "contacting",
     "by": "Айгерим Дюсенова"}
  ],

  "converted": {"student_id": null, "person_id": null}
}
```

`student_age` вместе с минимальным возрастом направления даёт проверку:
барабаны с 5 лет, скрипка с 7. Если возраст меньше — это не ошибка,
а предупреждение в интерфейсе.

### `POST /api/v1/leads`

Заведение вручную — администратор принял звонок.

```json
{"name": "Ольга Ким", "phone": "+77015559876",
 "student_name": "Ольга", "student_age": 34,
 "discipline_id": "...", "branch_id": "...",
 "source": "phone", "comment": "хочет вечером после 19"}
```

Ответ `201` — заявка целиком. Дубль по телефону в незакрытых стадиях —
`409` со ссылкой на существующую заявку: заводить второго лида на того же
человека нельзя, иначе воронка начнёт врать.

### `PATCH /api/v1/leads/{id}`

Смена стадии, назначение ответственного, напоминание, счётчик попыток.

```json
{"stage": "contacting", "assigned_to": "...",
 "next_action_at": "2026-08-12T18:00:00+05:00",
 "contact_attempts": 2, "lost_reason": null}
```

- Каждая смена стадии пишет строку в `lead_stage_history`. Без неё нельзя
  посчитать ни конверсию, ни время простоя — а это половина ценности этапа.
- Переход в `lost` без `lost_reason` — `422`. База это тоже запрещает,
  ошибку нужно перевести в понятный текст.
- Переход в `won` вручную запрещён — `422` с пояснением, что выигрыш
  ставит конверсия. Иначе появятся выигранные заявки без ученика.

### `POST /api/v1/leads/{id}/trial`

Назначение пробного урока. Создаёт занятие в расписании и переводит
заявку в `trial_booked` одной транзакцией.

```json
{"teacher_id": "...", "room_id": "...",
 "starts_at": "2026-08-12T13:00:00+05:00", "duration_min": 45,
 "price": 2000, "overbook_ack": false}
```

Ответ `201`:

```json
{"lesson_id": "...", "stage": "trial_booked",
 "starts_at": "2026-08-12T13:00:00+05:00",
 "teacher": "Егор Мадратов", "room": "Барабанная A",
 "notification_queued": true}
```

- Занятость кабинета и преподавателя проверяет база. `409` с указанием,
  кем занят слот, и предложением подтвердить овербукинг.
- Ставит в очередь `notification` напоминание за сутки с ключом
  идемпотентности `trial_reminder:<lesson_id>` — повторное назначение
  не должно слать второе сообщение.
- Кабинет обязан подходить направлению: барабаны требуют установки
  (`room.features` против `discipline.room_reqs`). Несоответствие — `422`.

### `POST /api/v1/leads/{id}/convert`

Конверсия в ученика. Самая тяжёлая операция этапа: одной транзакцией
создаёт персону, ученика, семью и, если передан тариф, продаёт абонемент.

```json
{
  "payer": {"first_name": "Гульнара", "last_name": "Сагындык",
            "phone": "+77015552418"},
  "student": {"first_name": "Алиса", "last_name": "Ким",
              "birth_date": "2019-03-14",
              "discipline_id": "...", "branch_id": "...",
              "main_teacher_id": "..."},
  "subscription": {"plan_id": "...", "starts_on": "2026-08-15",
                   "discount_pct": 0, "promo_code": "RS25",
                   "payment": {"amount": 48600, "method": "kaspi"}}
}
```

- `payer` необязателен: у взрослого ученика плательщик — он сам,
  тогда семья создаётся из одного человека.
- `subscription` необязателен: можно завести ученика и продать абонемент
  позже. Заявка всё равно переходит в `won`.
- Если персона с таким телефоном уже есть — переиспользуйте её,
  а не создавайте вторую. Тот же человек может привести второго ребёнка,
  и разводить ему два профиля значит потерять семейную скидку.
- Продажа абонемента идёт **через тот же код, что и в этапе 2**.
  Второй реализации быть не должно.

Ответ `201`:

```json
{"student_id": "...", "person_id": "...", "family_id": "...",
 "subscription_id": "...", "stage": "won"}
```

### `POST /api/v1/hooks/leads`

Приём заявок от внешних систем: `Telegram-Bot`, `LeadHub`, формы сайта.

Аутентификация — заголовок `X-Api-Key`, ключ ищется по хешу в `api_key`.
Заголовки `X-Tenant-Id` и `X-User-Id` здесь **не используются**: они
заглушка внутренней авторизации, их знает кто угодно, и подставить чужую
школу было бы тривиально. Тенант определяется ключом.

```json
{
  "external_id": "leadhub-8f21c3",
  "name": "Санжар Тлеу", "phone": "8 701 555 33 22",
  "student_name": "Санжар", "student_age": 13,
  "discipline": "барабаны",
  "source": "telegram_bot",
  "utm": {"utm_source": "instagram", "utm_campaign": "august"},
  "comment": "удобно после 18:00"
}
```

Требования:

- **Идемпотентность обязательна.** Повторная доставка того же
  `external_id` возвращает `200` с существующей заявкой, а не создаёт
  вторую. `LeadHub` устроен на ретраях: без этого одна недоступность сети
  превратится в дубли в воронке.
- Телефон нормализуется к E.164 из любого формата записи.
- `discipline` приходит строкой от бота — сопоставьте с направлением
  школы по названию без учёта регистра; не нашли — оставьте `null`,
  но заявку примите. Терять лид из-за опечатки в названии нельзя.
- Ключ без `leads:write` в `scopes` — `403`.
- Отзыв ключа (`revoked_at`) — `401`.
- Отметьте `api_key.last_used_at`.

### `GET /api/v1/leads/funnel?from=&to=`

Отчёт, ради которого этап затевался.

```json
{
  "period": {"from": "2026-07-01", "to": "2026-08-11"},
  "stages": [
    {"stage": "new", "entered": 84, "moved_on": 71, "conversion_pct": 85}
  ],
  "sources": [
    {"source": "telegram_bot", "leads": 31, "trials": 22, "won": 14,
     "conversion_pct": 45, "avg_days_to_won": 3.4}
  ],
  "lost_reasons": [{"reason": "price", "count": 9}],
  "avg_days_to_won": 4.1
}
```

Считается из `lead_stage_history`, а не из текущих стадий: заявка,
дошедшая до покупки, уже не лежит в колонке «пробный проведён»,
и без истории конверсия была бы посчитана неверно.

## Требования к бэкенду

- Смена стадии и запись истории — одна транзакция. История без стадии
  или стадия без истории одинаково ломают отчёт.
- Назначение пробного и конверсия — тоже по одной транзакции каждая.
- Продажа абонемента при конверсии переиспользует код этапа 2.
- Ограничения базы (`lead_lost_reason_ck`, `lead_external_uniq`,
  `lesson_room_no_overlap`) превращаются в осмысленные `409` и `422`.
- Скрипт создания ключа: `scripts/make_api_key.py <tenant> <name>` —
  печатает ключ один раз и сохраняет только хеш.
- Тесты: идемпотентность вебхука по `external_id`; отзыв ключа даёт `401`;
  ключ чужой школы не создаёт заявку в нашей; смена стадии пишет историю;
  `lost` без причины отвергается; `won` вручную отвергается; конверсия
  создаёт ученика с абонементом и переиспользует персону с тем же
  телефоном; пробный урок занимает кабинет и конфликтует по расписанию;
  отчёт по воронке считается из истории.
- Демо-данные: заполните воронку так, чтобы доска выглядела как
  в прототипе — заявки на всех стадиях, разные источники, отказы
  с причинами, один пробный с конфликтом кабинета.

## Требования к фронтенду

- **Доска воронки** по мотивам прототипа: колонки по стадиям, карточки
  с источником, временем ожидания и флагами. Перетаскивание между
  колонками — если реализуете, обязательно с откатом при ошибке сервера;
  запасной вариант — смена стадии из карточки.
- **Карточка заявки**: контакты, история стадий, назначенный пробный,
  кнопки «Назначить пробный» и «Оформить ученика».
- **Диалог назначения пробного**: преподаватель, кабинет, время;
  занятые слоты видно до отправки, конфликт кабинета показывается
  сервером с предложением подтвердить овербукинг.
- **Диалог конверсии**: плательщик, ученик, выбор тарифа — с тем же
  предпросмотром итога, что в этапе 2. Абонемент необязателен.
- Заявка с возрастом ниже минимального для направления помечается
  предупреждением, но не блокируется: решает администратор.
- Отчёт по воронке: конверсия между стадиями и таблица по источникам.
- Состояния загрузки, пустой воронки и ошибки обязательны.
