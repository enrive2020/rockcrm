# Контракт этапа 4 — «Деньги и зарплаты»

Продолжение этапов [1](contract-v1.md), [2](contract-v2.md), [3](contract-v3.md).
Транспорт, аутентификация, формат ошибок и часовой пояс — оттуда.

Серверная часть реализована; формы ниже сняты с работающего API,
а не придуманы заранее. Фронтенд пишется по ним.

---

## Зачем

Зарплата начисляется от каждого проведённого занятия, платежи копятся —
но посмотреть это негде. Владелец не видит ни выручки, ни загрузки
кабинетов, ни оттока, а это те цифры, ради которых покупают CRM,
а не только ведут расписание.

## Общие правила

- Период — пара `from` / `to`, **включительно с обеих сторон**. Без них
  берётся текущий месяц в поясе школы.
- Деньги — целое число тенге.
- Даты занятий берутся **в поясе филиала**: занятие в 20:00 по Алматы
  для базы в UTC приходится на предыдущие сутки, и последний день месяца
  уехал бы в соседний период.

## Ведомость

### `GET /api/v1/payroll?from=&to=&branch_id=`

```json
{
  "period": {"from": "2026-08-01", "to": "2026-08-31"},
  "closed": false, "period_id": null, "closed_at": null, "closed_by": null,
  "teachers": [{
    "teacher": {"id": "…", "name": "Дмитрий Шарапов", "color": "#A65D3F"},
    "lessons": 62, "entries": 71,
    "rate": 4500, "rate_varies": false,
    "no_shows": 3,
    "accrued": 292500, "corrections": -4500, "bonuses": 0, "total": 288000,
    "carried_over": -4500, "carried_over_entries": 1
  }],
  "totals": {"teachers": 5, "lessons": 259, "entries": 271, "no_shows": 7,
             "accrued": 0, "corrections": 0, "bonuses": 0, "total": 0,
             "carried_over": 0, "carried_over_entries": 0},
  "note": "Период открыт. В сумму вошли начисления за уже закрытые месяцы…"
}
```

- `lessons` — уникальные занятия, `entries` — строк начислений: у группы
  из четырёх человек занятие одно, а начислений четыре.
- `rate` — самая частая сумма начисления, `rate_varies` говорит, что она
  не единственная. Показывать ставку одним числом, когда их несколько,
  значит вводить в заблуждение.
- `carried_over` — сколько из суммы приехало правками за уже закрытые
  месяцы. Это не ошибка, а нормальный ход вещей, и он должен быть виден.

### `GET /api/v1/payroll/teachers/{staff_id}?from=&to=&branch_id=`

Расшифровка. `totals` той же формы, что строка ведомости, плюс:

```json
{
  "entries": [{
    "id": 30501, "date": "2026-07-01",
    "starts_at": "2026-07-01T13:00:00+05:00",
    "kind": "lesson", "lesson_id": "…",
    "student": "Мирас Сагындык", "discipline": "Фортепиано",
    "branch": "Аль-Фараби 53В",
    "duration_min": 55, "mark": "came", "amount": 4000,
    "calc": {"kind": "fixed", "mark": "came", "rate": 4000,
             "share": 1.0, "amount": 4000},
    "carried_over": false
  }]
}
```

`calc` — снимок расчёта. Без него через полгода невозможно объяснить
преподавателю, откуда взялась сумма.

### `GET /api/v1/payroll/periods?limit=`

```json
[{"id": "…", "period": {"from": "2026-07-01", "to": "2026-07-31"},
  "closed": true, "closed_at": "2026-08-01T10:00:00+05:00",
  "closed_by": "Асель Нурланова",
  "teachers": 10, "entries": 682, "total": 2730700}]
```

### `POST /api/v1/payroll/periods`

```json
{"from": "2026-07-01", "to": "2026-07-31"}
```

Ответ `201` — что именно закрыто, включая человеческую формулировку
для показа администратору.

Ошибки: `409 period_overlap` (пересечение с уже закрытым), `422
period_not_over` (период ещё не закончился), `400 bad_period`.

**Открытого периода не существует.** Строка заводится сразу закрытой:
пока месяц не закрыт, ведомость собирается из непроштампованных
начислений. Обратной операции нет — ошибка чинится корректировкой
в следующем периоде, а не переоткрытием.

Незакончившийся период закрыть нельзя: занятия, которые в нём ещё
пройдут, целиком уехали бы корректировкой.

## Отчёты

### `GET /api/v1/reports/revenue?from=&to=&branch_id=`

Разрезы по филиалам, направлениям, месяцам и способам оплаты.
Платёж, не привязанный к абонементу, попадает в строку
`{"id": null, "name": "Не распределено"}` — иначе сумма разрезов
не сошлась бы с итогом, а несходящийся финансовый отчёт хуже отсутствующего.

### `GET /api/v1/reports/rooms?from=&to=&branch_id=`

Загрузка в процентах, по филиалам и по кабинетам; список отсортирован
по загрузке — отчёт отвечает на вопрос «где кончилось место».

Ёмкость считается как часы работы филиала × дни с занятиями × кабинеты.
`capacity_note` объясняет формулу прямо в ответе: процент загрузки
без указания базы — число, которому нельзя верить.

### `GET /api/v1/reports/churn?from=&to=&grace_days=14&limit=50`

Отток с разрезом по преподавателям и поимённым списком ушедших.

> **Внимание:** текущая реализация считает отток по абонементам,
> а не по ученикам, и завышает его в разы — см. [#25](https://github.com/enrive2020/rockcrm/issues/25).
> Интерфейс должен показывать это число только после исправления.

### `GET /api/v1/reports/debts?limit=50`

Долг = начислено по абонементам семьи минус поступившие платежи.
Периода нет: долг — состояние на сейчас, а не за отрезок.
Формула совпадает с карточкой семьи, на это есть тест.

### `GET /api/v1/reports/summary?from=&to=&branch_id=`

Шапка экрана: выручка со сравнением с прошлым периодом, загрузка,
отток, ведомость и блок «требует внимания» (долги, кончающиеся
абонементы, открытые отработки, замороженные).

`change_pct` равен `null`, когда прошлого периода нет: «+100%» от нуля
читается как рост, хотя означает лишь появление первых данных.

## Требования к фронтенду

- Экран «Деньги и ЗП» по мотивам `prototype/index.html`: сводка сверху,
  ведомость таблицей, отчёты вкладками.
- Ведомость раскрывается в расшифровку по занятиям.
- Закрытие периода — действие с подтверждением, где показано, что именно
  будет закрыто: сколько начислений и на какую сумму. **Обратной операции
  нет**, и об этом нужно предупредить до нажатия, а не после.
- `carried_over` показывать отдельно — это правки за прошлые месяцы,
  и бухгалтер должен видеть их, а не искать расхождение.
- Отток пока не выводить: число неверно, см. #25.
- Снять обход в `AttendancePanel.tsx`: сервер теперь отдаёт
  `applied_effect` — факт из журнала, а не пересчёт правил.
