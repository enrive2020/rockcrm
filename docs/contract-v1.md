# Контракт этапа 1 — «Расписание и отметка посещаемости»

Договорённость между бэкендом и фронтендом. Обе стороны реализуются
параллельно и не ждут друг друга: фронтенд работает против моков,
собранных строго по этому документу.

**Документ первичен.** Если чего-то не хватает — реализуйте разумно
и опишите пробел в отчёте. Менять контракт в одностороннем порядке нельзя:
вторая сторона уже пишет код по нему.

---

## Границы этапа

Берём вертикальный срез: **расписание на день и отметка посещаемости
со всеми последствиями**. Отметка тянет за собой абонемент и зарплату —
разрезать это на «сначала расписание, потом деньги» нельзя, иначе получится
половина механизма, которую нельзя показать.

Входит:

- Расписание филиала на дату: дорожки преподавателей с занятиями
- Карточка занятия с предпросмотром последствий каждой отметки
- Отметка посещаемости: списание с абонемента, начисление преподавателю,
  выдача отработки
- Отмена ошибочной отметки компенсирующими записями

Не входит: воронка заявок, кабинет родителя, уведомления, продажа
абонементов, серии занятий (только чтение уже созданных занятий),
редактирование расписания.

## Структура репозитория

```
backend/     — FastAPI, слой доступа к БД, бизнес-логика   ← агент «бэкенд»
frontend/    — React + TypeScript, экран расписания        ← агент «фронтенд»
db/          — миграции                                     не трогать
docs/        — спецификация и этот контракт                 не трогать
prototype/   — визуальный ориентир                          не трогать
tests/       — тесты схемы                                  не трогать
```

Каждая сторона правит только свою папку. Пересечение файлов — ноль,
поэтому объединение результатов сводится к проверке, а не к разбору
конфликтов.

## Общие правила

- Комментарии, документация и сообщения об ошибках — **на русском**.
- Комментарий объясняет **почему**, а не пересказывает код.
- Зависимости фиксируются с версиями и сопровождаются комментарием, зачем.
- Ошибка сообщает, что произошло и что делать, — без извинений и общих слов.

## Транспорт

Базовый путь `/api/v1`. Тела запросов и ответов — JSON, UTF-8.
Все моменты времени — строки ISO 8601 с явным смещением: `2026-08-12T11:00:00+05:00`.
Идентификаторы — UUID-строки. Деньги — целое число тенге, без копеек.

Смещение отдаётся в поясе филиала и **никогда не задаётся цифрой в коде**:
Казахстан с марта 2024 живёт в едином поясе UTC+5, и захардкоженный `+06`
из прежних примеров сдвигал бы всё расписание на час. Пояс задаётся именем
(`Asia/Almaty`), правила смещения берёт база.

### Аутентификация на этом этапе

Временно, до появления входа: каждый запрос несёт заголовки

```
X-Tenant-Id: <uuid школы>
X-User-Id:   <uuid учётной записи>
```

Бэкенд обязан на каждый запрос выставлять тенант в соединение
(`SELECT set_config('app.tenant_id', $1, true)`) внутри транзакции.
Отсутствие заголовка — `401`.

Это заглушка, и она должна быть помечена `TODO` в коде: настоящая
авторизация приходит на следующем этапе, но контур изоляции обязан
работать уже сейчас.

### Формат ошибки

```json
{
  "error": {
    "code": "room_busy",
    "message": "Кабинет «Барабанная A» занят с 11:00 до 11:55",
    "details": {"lesson_id": "..."}
  }
}
```

| HTTP | Когда |
|---|---|
| 400 | Тело не прошло валидацию |
| 401 | Нет заголовков тенанта или пользователя |
| 404 | Объект не найден или принадлежит другому тенанту |
| 409 | Конфликт состояния: занятие уже отмечено, кабинет занят |
| 422 | Операция запрещена правилами: нет занятий на абонементе |

Ограничения базы (`lesson_room_no_overlap`, `lesson_teacher_no_overlap`,
`subscription_entry_once`) обязаны превращаться в осмысленные `409`,
а не в `500`.

## Ресурсы

### `GET /api/v1/branches`

```json
[{"id": "...", "name": "Аль-Фараби 53В", "timezone": "Asia/Almaty",
  "opens_at": "10:00", "closes_at": "21:00"}]
```

### `GET /api/v1/schedule?branch_id=<uuid>&date=<YYYY-MM-DD>`

Главный запрос интерфейса. Возвращает дорожки преподавателей —
ровно та структура, которую рисует расписание.

```json
{
  "date": "2026-08-12",
  "branch": {"id": "...", "name": "Аль-Фараби 53В",
             "opens_at": "10:00", "closes_at": "21:00"},
  "tracks": [
    {
      "teacher": {"id": "...", "name": "Дмитрий Шарапов",
                  "disciplines": ["Барабаны"], "color": "#A65D3F"},
      "lessons": [
        {
          "id": "...",
          "starts_at": "2026-08-12T11:00:00+05:00",
          "ends_at":   "2026-08-12T11:55:00+05:00",
          "duration_min": 55,
          "kind": "regular",
          "status": "planned",
          "title": "Амина Сагындык",
          "student_id": "...",
          "room": {"id": "...", "name": "Барабанная A"},
          "attendance_mark": null,
          "conflicts": [
            {"kind": "room", "with_lesson_id": "...",
             "message": "Кабинет «Барабанная A» занят"}
          ]
        }
      ]
    }
  ],
  "summary": {"lessons": 12, "trials": 1, "conflicts": 1,
              "room_utilization_pct": 74}
}
```

- `kind`: `regular` | `trial` | `makeup` | `extra`
- `status`: `planned` | `held` | `cancelled`
- `attendance_mark`: `null` пока не отмечено, иначе значение из таблицы отметок
- `title`: имя ученика, название группы или имя из заявки для пробного
- Дорожки — только преподаватели, у которых есть занятия в этот день,
  в порядке первого занятия
- `conflicts` считается сервером. Пересечения по кабинету и преподавателю
  попадают в базу только с подтверждённым овербукингом, но показывать
  их всё равно нужно
- Занятия со `status = cancelled` не возвращаются

### `GET /api/v1/lessons/{id}`

Карточка занятия для панели отметки. **Ключевой момент этапа**: ответ
содержит просчитанные последствия каждой возможной отметки, чтобы интерфейс
показал их до подтверждения, а не после.

```json
{
  "id": "...",
  "starts_at": "2026-08-12T11:00:00+05:00",
  "ends_at": "2026-08-12T11:55:00+05:00",
  "duration_min": 55,
  "kind": "regular",
  "status": "planned",
  "room": {"id": "...", "name": "Барабанная A"},
  "teacher": {"id": "...", "name": "Дмитрий Шарапов", "rate": 4500},
  "participants": [
    {
      "student_id": "...",
      "name": "Амина Сагындык",
      "attendance": null,
      "subscription": {
        "id": "...",
        "lessons_total": 8,
        "lessons_balance": 5,
        "makeups_balance": 1,
        "valid_until": "2026-08-31",
        "status": "active"
      },
      "mark_effects": {
        "came": {
          "lessons_delta": -1, "makeups_delta": 0, "teacher_amount": 4500,
          "lessons_after": 4,
          "summary": "Спишется 1 занятие, останется 4. Преподавателю 4 500 ₸."
        },
        "late":              {"...": "то же, что came"},
        "no_show":           {"...": "по правилам абонемента"},
        "cancelled_early":   {"...": "..."},
        "cancelled_late":    {"...": "..."},
        "cancelled_teacher": {"...": "..."}
      }
    }
  ],
  "note": {"body": "...", "homework": "...", "tags": ["..."]}
}
```

`mark_effects` считается **из правил конкретного абонемента**
(`subscription.rules`), а не из текущих настроек школы: проданный абонемент
живёт по условиям момента покупки. Ключи — все шесть значений отметки.
Групповое занятие даёт несколько участников, у каждого свои эффекты.

Если у ученика нет действующего абонемента, `subscription` равен `null`,
а в эффектах `lessons_delta = 0` и приписка, что занятие пойдёт разовой
оплатой.

### `POST /api/v1/lessons/{id}/attendance`

```json
{"student_id": "...", "mark": "came"}
```

Ответ `201` — фактически применённые последствия:

```json
{
  "attendance_id": "...",
  "mark": "came",
  "applied": {
    "lessons_delta": -1,
    "lessons_after": 4,
    "makeups_delta": 0,
    "teacher_amount": 4500,
    "teacher_id": "...",
    "subscription_id": "..."
  },
  "lesson_status": "held",
  "alerts": [
    {"kind": "subscription_low",
     "message": "Осталось 2 занятия — пора предложить продление"}
  ]
}
```

Требования к реализации:

- Всё внутри **одной транзакции**: отметка, запись в журнал абонемента,
  начисление зарплаты, запись в аудит. Частично применённая отметка
  недопустима — она разошлась бы с деньгами.
- Повторная отметка того же ученика на том же занятии — `409`.
  Уникальный индекс в базе уже это гарантирует, ошибку нужно перевести.
- Списание при нулевом остатке — `422` с внятным текстом, а не уход в минус.
- `alerts` появляется, когда остаток опустился до 2 и ниже.
- Занятие получает `status = held` после первой отметки.

### `DELETE /api/v1/attendance/{id}`

Отмена ошибочной отметки. Возвращает `200` с описанием компенсации.

Записи журнала **не удаляются и не правятся** — база это запрещает
и вернёт `restrict_violation`. Отмена добавляет обратные записи
(`refund` в журнал абонемента, `correction` в зарплату) и проставляет
`attendance.revoked_at`.

## Требования к бэкенду

Стек: Python 3.12+, FastAPI, psycopg 3, pydantic v2. ORM не нужен —
запросы пишутся на SQL: схема уже несёт логику, и прятать её за ORM значит
дублировать правила в двух местах.

- Подключение — пул psycopg. На каждый запрос: транзакция, `set_config`
  тенанта, работа под ролью `rockcrm_app`.
- Правила отметки вычисляются **одной функцией**, которую используют
  и предпросмотр в `GET /lessons/{id}`, и применение в `POST`. Расхождение
  между «что обещали» и «что сделали» — худший из возможных багов здесь.
- Тесты на pytest против настоящей базы (`DATABASE_URL`), схема применяется
  из `db/`. Обязательно покрыть: предпросмотр совпадает с применением;
  повторная отметка отвергается; отмена возвращает баланс ровно назад;
  чужой тенант получает 404.
- `backend/README.md`: как поднять, как прогнать тесты, какие переменные окружения.

## Требования к фронтенду

Стек: React 18+, TypeScript, Vite. Библиотеку состояния и стилей выбирайте
сами, но обоснуйте выбор в README.

- **Визуальный ориентир — `prototype/index.html`.** Оттуда берутся палитра,
  шрифты, логика расписания как многодорожечного секвенсора и панель отметки.
  Это не пиксель-в-пиксель, но узнаваемость обязательна. Токены цвета
  и типографики перенесите в CSS-переменные, обе темы поддержите.
- Типы ответов API описываются в TypeScript **вручную по этому контракту**
  и живут в одном файле — он же граница с бэкендом.
- Режим моков включается переменной окружения и отдаёт данные,
  собранные по контракту. Без него разработка блокируется бэкендом.
- Экран расписания: выбор филиала и даты, дорожки, конфликты видны,
  клик по занятию открывает панель.
- Панель отметки: выбор одной из шести отметок, **последствия показаны
  до подтверждения** из `mark_effects`, подтверждение шлёт `POST`
  и обновляет расписание.
- Состояния загрузки, пустого дня и ошибки — обязательны. Ошибка
  показывает `message` от сервера.
- `frontend/README.md`: как запустить, как включить моки, какие решения
  приняты и почему.
