# API-контракт Подача.AI (REST, v1)

Машиночитаемый контракт: [`openapi.yaml`](openapi.yaml) (OpenAPI 3.1). Этот документ объясняет правила, которые в YAML не выражаются полностью, и фиксирует решения. Связанные документы: `prd.md` (роли, RBAC, модули), `sales/product-roadmap.md` §3 (модульный монолит, NestJS/FastAPI, Yandex Cloud), `research/00-strategy.md` §2 (мы не платёжный агент, касса заведения фискализирует чек).

Пометка **[Р-n]** — принятое решение (сводка в §12).

---

## 1. Общие принципы

| Правило | Значение |
|---|---|
| Базовый URL | `https://api.podacha.ai/v1`, sandbox `https://api.sandbox.podacha.ai/v1` |
| Хостинг | Yandex Cloud `ru-central1`; ПДн гостей не покидают РФ (152-ФЗ, ст. 18 ч. 5 — локализация) |
| Формат | JSON UTF-8; `snake_case` в полях; ошибки `application/problem+json` (RFC 9457) |
| Идентификаторы | строка «префикс + ULID»: `org_`, `ven_`, `tbl_`, `ord_`, `pay_`, `bkg_`, `rev_`, `gst_`, `usr_`, `evt_` [Р-6] |
| Деньги | целые копейки (`integer`), валюта всегда RUB [Р-7] |
| Время | RFC 3339 в UTC (`2026-11-01T18:30:00Z`); у точки есть `timezone` для отображения и слотов броней |
| Частичное обновление | `PATCH` с `application/merge-patch+json` (RFC 7396) + `If-Match: <etag>` |
| Действия, не CRUD | суффикс `:action` (`/orders/{id}:transition`, `/tables/{id}/qr:rotate`) |
| Язык | `Accept-Language` или `?locale=`; тексты ошибок `title`/`detail` на языке запроса, `code` — всегда английский |
| Трассировка | ответ всегда содержит `X-Request-Id`; клиент может передать свой |

## 2. Аутентификация и роли

### 2.1. Три типа субъектов

| Субъект | Как получает токен | Токен | TTL | Где используется |
|---|---|---|---|---|
| Персонал (`owner`, `manager`, `staff`) | `/auth/login` (пароль или OTP по SMS/Telegram/MAX) | access JWT (ES256) + непрозрачный refresh | 15 мин / 30 дней, ротация при каждом `/auth/refresh` | админка, панель официанта, бот персонала |
| Гость | `/guest/sessions` по QR-токену стола | guest JWT, `aud=guest` | 4 часа, продление новой сессией | веб-меню (PWA) |
| Сервер-сервер (партнёр, интегратор, свой бот) | API-ключ в кабинете, обмен на JWT по OAuth2 client_credentials (`/auth/token`, этап L1) | access JWT, `aud=api` | 1 час | интеграции, реселлеры `partner` |

Refresh-токены храним хешированными; повторное использование уже ротированного refresh-токена отзывает всю цепочку (защита от кражи). Для `staff` на общих планшетах есть короткий вход по PIN поверх устройства, привязанного управляющим (L1).

### 2.2. Claims access JWT

```json
{
  "iss": "https://api.podacha.ai",
  "sub": "usr_01JC...",
  "aud": "admin",
  "org": "org_01JA...",
  "roles": [{"r": "owner", "v": "*"}, {"r": "manager", "v": ["ven_01JB..."]}],
  "scp": ["menu:write", "orders:write"],
  "iat": 1761840000, "exp": 1761840900, "jti": "..."
}
```

Guest JWT: `sub` = id сессии, `org`, `ven`, `tbl`, `aud=guest`, без ПДн [Р-2]. Ключи подписи публикуются в `/.well-known/jwks.json`, ротация раз в 90 дней.

### 2.3. Авторизация

Решение принимается в два шага: **роль → разрешение (scope)** и **проверка арендатора и точки** (`org_id` из токена, `venue_id` из пути должен входить в `roles[].v`). Матрица прав — в `prd.md` §3.3; маппинг на scopes:

| Scope | owner | manager | staff | partner |
|---|---|---|---|---|
| `org:billing`, `users:write`, `guests:export` | да | — | — | — |
| `venues:write`, `menu:write`, `bookings:write`, `reviews:write`, `ai:config` | да | да (свои точки) | — | по договору |
| `orders:write`, `calls:write` | чтение | да | да (свои столы/зона) | — |
| `stoplist:write` | да | да | если разрешено в точке | — |
| `guests:read` | да (полные ПДн) | да (телефон маскирован) | — | — |
| `analytics:read` | да | своя точка | — | агрегаты |
| `audit:read` | да | своя точка | — | — |

Чужой ресурс возвращает **404, а не 403**, чтобы не раскрывать существование объектов другого арендатора [Р-3]. 403 — только когда объект виден, но действие запрещено (например, `manager` пытается экспортировать гостей).

`support` получает доступ только через тикет: временный токен с `act` (impersonation claim, RFC 8693), TTL 1 ч, каждое действие пишется в audit log клиента.

## 3. Гостевой контур (QR-токен стола)

### 3.1. QR-токен

| Свойство | Значение |
|---|---|
| Формат | 22 символа base64url (128 бит случайности), не содержит id стола или точки |
| URL на табличке | `https://m.podacha.ai/t/{qr_token}` |
| Хранение | в БД — SHA-256 токена; поиск по хешу |
| Перевыпуск | `POST /venues/{id}/tables/{id}/qr:rotate`; старый токен → `410 Gone` с подсказкой «попросите официанта» |
| Статичность | токен постоянный (печатаем табличку один раз); защита от «заказов из дома» — см. 3.3 |

### 3.2. Поток гостя

| Шаг | Вызов | Примечание |
|---|---|---|
| 1 | `POST /guest/sessions {qr_token}` | возвращает guest JWT, точку, стол, доступные `features` по тарифу |
| 2 | `GET /guest/menu` | `ETag`, `Cache-Control: max-age=60`; стоп-лист применён, `available=false` |
| 3 | `POST /guest/ai/messages` | SSE-стрим; цены и наличие ИИ получает только через function calling к БД |
| 4 | `POST /guest/orders` + `Idempotency-Key` | сервер пересчитывает цены сам; цена клиента не принимается |
| 5 | `POST /guest/calls` | «позвать официанта» / «счёт» |
| 6 | `GET /guest/bill` | счёт из POS (iiko/Poster) или из наших заказов |
| 7 | `POST /guest/payments` | возвращает `confirmation.url` (СБП-ссылка `qr.nspk.ru` / платёжная форма эквайера) |
| 8 | `GET /guest/payments/{id}` | поллинг раз в 2 с до 2 мин, финальный статус приходит вебхуком эквайера |
| 9 | `POST /guest/reviews` | 1–3★ — внутренний отзыв и алерт управляющему; 4–5★ — `redirect_url` на Яндекс Карты/2ГИС (без давления, без вознаграждения за оценку) |
| 10 | `POST /guest/consents` | только если гость вводит телефон (бронь, лояльность) |

### 3.3. Защита гостевых эндпоинтов

| Риск | Мера |
|---|---|
| Перебор QR-токенов | 128 бит + лимит 20 `/guest/sessions` в минуту на IP, Yandex Smart Web Security перед API |
| Заказ «из дома» по фото таблички | заказ без оплаты требует подтверждения официантом (`new → accepted`); точка может включить «только в часы работы» и лимит суммы неподтверждённого заказа (по умолчанию 15 000 ₽) |
| Спам вызовами | 1 вызов одной причины в 60 с на стол |
| Расход LLM | 30 сообщений ИИ-официанту на сессию, 1000 символов на сообщение; сверх — `429` с `code=AI_QUOTA_EXCEEDED` |
| Утечка ПДн | гостевые ответы никогда не содержат телефонов и имён других гостей и персонала (официант — только имя для чаевых) |

## 4. Админ-эндпоинты

Все пути — в контексте организации из токена; точка — сегмент пути `/venues/{venue_id}/...` [Р-4].

| Группа | Эндпоинты | Роли | MVP / L1 |
|---|---|---|---|
| Профиль | `GET /me`, `/auth/*` | все | MVP |
| Точки, столы, QR | `/venues`, `/venues/{id}`, `/venues/{id}/tables`, `qr:rotate` | owner (создание), manager | MVP |
| Меню | `/venues/{id}/menu`, `/menu/items`, `/stop-list` | owner, manager; staff — стоп-лист | MVP |
| Заказы и вызовы | `/venues/{id}/orders`, `orders/{id}:transition`, `/calls`, `/events` (SSE) | manager, staff | MVP |
| Брони | `/venues/{id}/bookings` | manager; staff — чтение на сегодня | MVP |
| Отзывы | `/venues/{id}/reviews`, `reviews/{id}/reply` | owner, manager | MVP |
| CRM | `/guests`, `DELETE /guests/{id}`, `/guests/exports` | owner; manager — без экспорта | L1 |
| Пользователи | `/users`, `/users/invitations`, `/audit-log` | owner | MVP |
| Аналитика, OCR, смены | `/venues/{id}/analytics/*`, `/invoices`, `/shifts` | — | L1–L2, отдельный раздел контракта |
| Подписки | `/webhook-endpoints` | owner, partner | L1 |

### 4.1. Статусная машина заказа

| Из | Действие | В | Кто |
|---|---|---|---|
| — | создание гостем | `new` | guest |
| `new` | `accept` | `accepted` → автоматически `sent_to_pos` при подключённой POS | staff/manager |
| `new` | `reject` (+ `reason`) | `rejected` | staff/manager |
| `new` | 3 мин без реакции | эскалация управляющему (событие, статус не меняется) | system |
| `accepted`/`sent_to_pos` | `serve` | `served` | staff |
| любой открытый | `payment.succeeded` на полную сумму счёта | `paid` | system |
| `paid`/`served` | `close` | `closed` | staff/system (закрытие стола в POS) |

Недопустимый переход → `409 ORDER_INVALID_TRANSITION`.

### 4.2. Реальное время

Панель официанта получает события через `GET /venues/{id}/events` (Server-Sent Events, `Last-Event-ID` для догрузки после разрыва, буфер 24 ч). WebSocket не используем на MVP: SSE проще проксировать через API Gateway и балансировщик Yandex Cloud [Р-9]. Официант в Telegram/MAX получает те же события через Channel Gateway.

## 5. Версионирование

| Правило | Значение |
|---|---|
| Мажорная версия | в пути: `/v1`. `/v2` только при несовместимых изменениях, параллельная поддержка `v1` — не меньше 12 месяцев |
| Совместимые изменения | новые поля, эндпоинты, значения enum — без смены версии. Клиенты обязаны игнорировать неизвестные поля и терпимо относиться к новым enum-значениям |

| Устаревание | заголовки `Deprecation` (RFC 9745) и `Sunset` (RFC 8594), уведомление партнёрам за 90 дней |
| Changelog | `docs/product/api-changelog.md` (заводится с первым изменением) |
| Контроль | CI сравнивает `openapi.yaml` с main (oasdiff); несовместимое изменение в `v1` блокирует merge |

## 6. Ошибки

Формат — RFC 9457 Problem Details с расширениями `code`, `request_id`, `errors[]`:

```json
{
  "type": "https://docs.podacha.ai/errors/order-item-unavailable",
  "title": "Позиция недоступна",
  "status": 422,
  "detail": "«Сырники» закончились, выберите другое блюдо",
  "code": "ORDER_ITEM_UNAVAILABLE",
  "request_id": "req_01JD...",
  "errors": [{"pointer": "/items/0/item_id", "code": "STOP_LIST", "message": "в стоп-листе"}]
}
```

| HTTP | Когда | Примеры `code` |
|---|---|---|
| 400 | невалидный JSON, неизвестный параметр | `BAD_REQUEST` |
| 401 | нет/просрочен токен | `TOKEN_EXPIRED`, `TOKEN_INVALID`, `OTP_INVALID` |
| 403 | объект виден, действие запрещено | `FORBIDDEN_ROLE`, `FEATURE_NOT_IN_PLAN` |
| 404 | нет объекта или он чужой | `NOT_FOUND` |
| 409 | конфликт состояния | `ORDER_INVALID_TRANSITION`, `BOOKING_SLOT_TAKEN`, `MENU_MANAGED_BY_POS`, `BILL_CHANGED`, `IDEMPOTENCY_KEY_REUSED` |
| 410 | отозванный QR | `QR_REVOKED` |
| 412 | `If-Match` не совпал | `PRECONDITION_FAILED` |
| 422 | бизнес-валидация | `VALIDATION_FAILED`, `ORDER_ITEM_UNAVAILABLE`, `AMOUNT_EXCEEDS_DUE` |
| 429 | лимиты | `RATE_LIMITED`, `AI_QUOTA_EXCEEDED` (+ `Retry-After`) |
| 502/503/504 | недоступна POS, эквайер или LLM | `POS_UNAVAILABLE`, `PAYMENT_PROVIDER_UNAVAILABLE`, `AI_UNAVAILABLE` |

Каталог `code` — стабильный контракт: значение не переименовывается в пределах `v1`. Фронт показывает `detail`, логика ветвится только по `code`.

## 7. Пагинация, фильтры, сортировка

| Правило | Значение |
|---|---|
| Тип | курсорная (keyset) по `(created_at, id)` [Р-5] |
| Параметры | `limit` (1–200, по умолчанию 50), `cursor` (непрозрачная base64url-строка, TTL 24 ч) |
| Ответ | `{"data": [...], "page": {"next_cursor": "...", "has_more": true}}` |
| Сортировка | `sort=-created_at` (минус — по убыванию); список допустимых полей указан у каждого эндпоинта |
| Фильтры | плоские query-параметры (`status=new,accepted`, `created_from`, `created_to`, `updated_since`) |
| Общее число | не отдаётся по умолчанию; `?include=total` разрешён в админке для списков до 10 000 строк |
| Синхронизация | `updated_since` + курсор — для партнёров и офлайн-кэша панели официанта |

Offset-пагинацию не используем: списки заказов и событий быстро растут, а offset даёт дубли и пропуски при вставках.

## 8. Идемпотентность, конкурентность, лимиты

| Механизм | Где | Правило |
|---|---|---|
| `Idempotency-Key` (UUID) | обязателен для `POST /guest/orders`, `/guest/payments`, `/bookings` | ключ хранится 24 ч в Redis вместе с хешем тела; тот же ключ + то же тело → тот же ответ; другое тело → `409 IDEMPOTENCY_KEY_REUSED` |
| `ETag` / `If-Match` | `PATCH` точек, позиций меню, броней | оптимистичная блокировка; без `If-Match` — last write wins (разрешено только админке) |
| `bill_version` | `POST /guest/payments` | если счёт в POS изменился (дозаказ), `409 BILL_CHANGED` — гость видит новый счёт до оплаты |
| Rate limit | все | персонал 600 запр./мин на пользователя; гость 120/мин на сессию; партнёр 1 200/мин на ключ; заголовки `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` |

## 9. Входящие вебхуки

### 9.1. Платежи

Мы не платёжный агент и не храним карточные данные: платёж создаётся на эквайринге **заведения** (его `shop_id` и ключи хранятся у нас в Yandex Lockbox), деньги идут на его счёт, чек 54-ФЗ выбивает облачная касса эквайера или касса заведения [Р-8]. URL уведомлений: `/v1/webhooks/payments/{provider}/{integration_id}`.

| Провайдер | Проверка подлинности | Ключевые события | Замечания |
|---|---|---|---|
| ЮKassa | подписи нет; проверяем IP из опубликованного allowlist и **обязательно** перезапрашиваем `GET /v3/payments/{id}` | `payment.succeeded`, `payment.canceled`, `refund.succeeded` | СБП — `payment_method_data.type=sbp`; чек — объект `receipt` |
| Т-Банк (T-Pay / эквайринг) | поле `Token` = SHA-256 от отсортированных значений + `Password` терминала | `Status`: `CONFIRMED`, `REJECTED`, `REFUNDED` | ответ строго `OK` телом, иначе повторы |
| Яндекс Пэй | JWT (ES256), проверка по JWKS Яндекса | `ORDER_STATUS_UPDATED` (`CAPTURED`, `FAILED`, `REFUNDED`) | режим для ресторанов — оплата по QR |
| Банк по СБП напрямую (партнёр-эквайер) | HMAC-SHA256 тела в `X-Signature` по секрету интеграции | `paid`, `expired`, `refunded` | динамический QR ОПКЦ СБП, TTL ссылки 10–30 мин |

Конкретные поля сверять с документацией провайдера при реализации адаптера; контракт ниже от них не зависит.

**Обработка (для всех провайдеров):**

| Шаг | Правило |
|---|---|
| 1 | проверить подлинность; при неудаче `401` и запись в security-лог |
| 2 | записать сырое событие в `inbound_events` (уникальный ключ `provider + event_id/payment_id + status`) — дубль → сразу `200` |
| 3 | нормализовать в внутреннее событие `payment.succeeded / failed / refunded`, обновить `Payment` в транзакции, увеличить `paid` у счёта |
| 4 | ответить `200` в течение 5 с; тяжёлое (закрытие стола в POS, чаевые, CRM) — асинхронно через outbox |
| 5 | сверка: каждые 15 мин джоба опрашивает зависшие `pending` старше 10 мин у провайдера |

Чаевые: отдельной операцией через сервис чаевых (CloudTips / Нетмонет) или как отдельная позиция у эквайера — по настройке точки; в `Payment.tip_amount` фиксируется итог. Мы не принимаем деньги на свой счёт.

### 9.2. POS

URL: `/v1/webhooks/pos/{provider}/{integration_id}`.

| POS | Аутентификация | События, которые слушаем | Что делаем |
|---|---|---|---|
| iikoCloud (iikoTransport) | `authToken`, заданный при регистрации вебхука, приходит в заголовке `Authorization` | `DeliveryOrderUpdate`/`TableOrderUpdate`, `StopListUpdate`, `ReserveUpdate` | обновляем статус заказа, стоп-лист (`stop_list.updated`), брони |
| Poster | подпись `verify` = md5(account + object + object_id + action + data + secret) | `incoming_order`, `transaction`, `product`, `dish` | синхронизация меню, закрытые чеки для аналитики |
| r_keeper (L2) | HMAC по секрету интеграции | изменения заказа и меню | по мере подключения |

Правила: тот же конвейер «проверить → сохранить сырое → дедупликация → асинхронная обработка». Меню из POS — источник истины: при подключённой POS ручная правка цены возвращает `409 MENU_MANAGED_BY_POS` (разрешены только фото, описания, переводы, теги). Если вебхуки POS не пришли, раз в 5 мин делаем pull стоп-листа (iiko `/api/1/stop_lists`) [Р-10].

## 10. Исходящие вебхуки

Клиент или партнёр подписывается через `POST /webhook-endpoints` (только `https://`, секрет выдаётся один раз).

| Свойство | Значение |
|---|---|
| Подпись | заголовки `Webhook-Id`, `Webhook-Timestamp`, `Webhook-Signature: v1,<base64(HMAC-SHA256(secret, id + "." + timestamp + "." + body))>` — по схеме Standard Webhooks |
| Окно времени | получатель отклоняет события старше 5 мин |
| Повторы | при не-2xx или таймауте 10 с: 30 с, 2 мин, 10 мин, 1 ч, 6 ч, 24 ч (до 3 суток); после 3 суток неудач endpoint отключается с письмом owner |
| Порядок | не гарантирован; у сущности есть `updated_at`, получатель применяет только более новое |
| ПДн | в событиях — id и маскированные данные; полные ПДн получатель берёт отдельным запросом с правами |
| Каталог | `order.created`, `order.status_changed`, `call.created`, `payment.succeeded`, `payment.failed`, `payment.refunded`, `tip.paid`, `booking.created/updated/cancelled`, `review.received`, `review.negative`, `menu.updated`, `stop_list.updated`, `guest.consent_changed` |

Пример:

```json
{
  "id": "evt_01JDZ...",
  "type": "review.negative",
  "api_version": "2026-11-01",
  "created_at": "2026-11-01T19:04:11Z",
  "org_id": "org_01JA...",
  "venue_id": "ven_01JB...",
  "data": {"review_id": "rev_01JD...", "source": "yandex_maps", "rating": 2, "excerpt": "Ждали заказ 40 минут"}
```

## 11. 152-ФЗ и безопасность в контракте

| Требование | Как отражено в API |
|---|---|
| Локализация ПДн в РФ (ст. 18 ч. 5) | один регион `ru-central1`; вебхуки и экспорт не отправляют полные ПДн за рубеж; LLM — YandexGPT/GigaChat в РФ |
| Согласие (ст. 9) с 01.09.2025 — отдельным документом | `POST /guest/consents` с `purpose` и `document_version`; согласие на рекламу (38-ФЗ ст. 18) — отдельный `purpose=marketing_messages` |
| Отзыв согласия, удаление (ст. 21) | `POST /guest/consents {granted:false}`, `DELETE /guests/{id}` — асинхронно, ≤ 10 рабочих дней |
| Минимизация | guest JWT без ПДн; `manager` видит маскированный телефон; события без ПДн |
| Журнал | все изменения и любой доступ к полным ПДн — в `audit_log` (`/audit-log`), хранение 3 года |
| Транспорт | TLS 1.2+ (с поддержкой ГОСТ-шифров на балансировщике — L2 при требовании клиентов), HSTS |
| Секреты интеграций | ключи эквайера и POS — в Yandex Lockbox, в API отдаются только последние 4 символа |

## 12. Ключевые решения

| # | Решение | Почему |
|---|---|---|
| Р-1 | Один REST API `v1` с OpenAPI 3.1 как источником истины; клиенты (PWA, админка, боты) генерируются из спецификации | одна команда 2–3 человека, модульный монолит |
| Р-2 | Гость без аккаунта: QR-токен стола (128 бит, хеш в БД) → guest JWT на 4 ч без ПДн | вход за 3 с, без ПДн до брони/лояльности |
| Р-3 | Персонал: ES256 access JWT 15 мин + ротируемый refresh 30 дней; RBAC = роль × точка; чужие объекты → 404 | изоляция арендаторов, отзыв доступа уволенного за ≤ 15 мин |
| Р-4 | Точка в пути (`/venues/{id}/...`), организация — из токена | явная проверка доступа к точке, удобно для сетей |
| Р-5 | Курсорная пагинация, без total по умолчанию | стабильность на растущих таблицах заказов и событий |
| Р-6 | ID = префикс + ULID | читаемость в логах, сортировка по времени |
| Р-7 | Деньги — целые копейки | без ошибок округления при делении счёта и чаевых |
| Р-8 | Платёж всегда на эквайринге заведения; вебхуки проверяются по правилам провайдера, а для ЮKassa статус перезапрашивается; обработка идемпотентна через `inbound_events` | мы не платёжный агент (00-strategy §2), защита от поддельных уведомлений |
| Р-9 | Реальное время через SSE, а не WebSocket | проще в инфраструктуре Yandex Cloud, достаточно для однонаправленных событий |
| Р-10 | POS — источник истины для меню и цен; вебхук + pull каждые 5 мин как страховка | цены ИИ берёт только из БД, стоп-лист не устаревает |
| Р-11 | Ошибки RFC 9457 со стабильным `code`; версия в пути + датированная версия событий; oasdiff в CI | предсказуемость для партнёров и интеграторов |
