# Схема базы данных RockCRM

PostgreSQL 17+. Файлы применяются по порядку номеров.

| Файл | Содержание |
|---|---|
| `001_core.sql` | Тенанты, персоны, филиалы, кабинеты, сотрудники, семьи, ученики, аудит |
| `002_scheduling.sql` | Серии занятий, занятия, посещаемость, заметки к урокам |
| `003_billing.sql` | Тарифы, абонементы, журнал движений, заморозки, отработки, платежи, зарплаты |
| `004_sales.sql` | Заявки, воронка, уведомления, задачи |
| `005_rls.sql` | Изоляция тенантов, роль приложения, защита журналов от правок |

## Требования

Единственное расширение — **`btree_gist`**. Входит в стандартный contrib
и есть в официальном образе `postgres`. Без него не создаются ограничения,
запрещающие двойную бронь кабинета и преподавателя — то есть отваливается
одна из главных гарантий схемы. Урезанные сборки Postgres (embedded,
некоторые managed-инстансы) его не содержат: наличие нужно проверить
до развёртывания.

```sql
SELECT * FROM pg_available_extensions WHERE name = 'btree_gist';
```

## Развёртывание

```bash
docker run -d --name rockcrm-pg \
  -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=rockcrm \
  -p 5432:5432 postgres:17-alpine

for f in 00*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"; done
```

## Как приложение подключается

Приложение ходит под ролью `rockcrm_app` — **не владельцем таблиц
и не суперпользователем**. Это принципиально: владелец и суперпользователь
проходят мимо политик изоляции, и вся защита превращается в декорацию.

Сразу после выдачи соединения из пула и внутри транзакции:

```sql
SET LOCAL app.tenant_id = '<uuid школы>';
```

`SET LOCAL` вместо `SET` — чтобы значение не пережило транзакцию и не утекло
в следующий запрос, который возьмёт то же соединение из пула для другой школы.

Если параметр не выставлен, `current_tenant()` вернёт NULL и запросы вернут
ноль строк. Забытый вызов даёт пустой экран, а не чужие данные — ошибка
громкая и безопасная.

## Что гарантирует база, а не код

- **Кабинет и преподаватель не могут быть заняты дважды.** Ограничения
  исключения, а не проверка в приложении: два администратора, сохраняющие
  занятие одновременно, оба увидели бы свободный слот.
- **Занятие не спишется дважды.** Уникальный индекс по отметке — защита
  от двойного клика и повторной обработки запроса.
- **Журнал абонемента и аудит нельзя переписать.** Ни UPDATE, ни DELETE
  под ролью приложения. Ошибки гасятся компенсирующими записями.
- **Строку нельзя записать в чужой тенант.** Политики проверяют не только
  чтение, но и запись.
- **Заморозки одного абонемента не перекрываются.** Иначе срок продлился бы
  дважды за одни и те же дни.

## Остаток абонемента

Поля `lessons_balance` и `makeups_balance` — **кэш**. Источник правды —
`subscription_entry`. Кэш пересчитывается триггером полным пересчётом суммы,
а не инкрементом: инкремент быстрее и однажды разъедется с журналом.

Сверка (должна возвращать ноль строк):

```sql
SELECT s.id, s.lessons_balance, sum(e.lessons_delta) AS actual
FROM subscription s JOIN subscription_entry e ON e.subscription_id = s.id
GROUP BY s.id, s.lessons_balance
HAVING s.lessons_balance <> sum(e.lessons_delta);
```
